### 8.1 Row 01: the 5 hex task ids in use

The finding is right about the count and changes claim (4) (Row 01 evidence). It does not change the fix:

- **The fix refuses none of them.** The refusal goes into `spool-fleet-relay.sh` only, the cross-machine hop. All 5 ids were sent locally on sat (no `@<box>` recipient), and a local send keeps its task id as it is (Row 01 evidence (3)). Those sends behave the same after the fix.
- **Refusing "only ids not in use" would keep the defect.** 4 of the 5 are short forms of real topics (`9da17538` is the 1588-line topic `9da17538-1993-…`). If one of them is sent to another machine today, it is hashed to `uuid5("spool-task:9da17538")`, a new empty topic, which is the defect. Accepting it at the relay because it is "in use" would send it there. Refusing it with "pass the full uuid" is the fix.
- **Who the refusal could stop:** a cross-machine reply in a thread that so far used a short id only locally (n=5 such ids on sat, 0 on <box2>). It gets exit 2 and the line asking for the full uuid, and nothing is sent, instead of a reply nobody reads.
- **Not this row:** a local send with a short topic id makes a local topic that is not the full one. 4 of the 5 ids are that case. Not measured: whether any reader missed a message because of it. It is a candidate for the next round, not a row here (R1: one defect per row).
