## 3. The open defects, and the smell behind each

Only these are still on master at 9699d4165. Everything else in section 2
has a fixing sha, is infra, a plant, or is by design.

### 3.1 The deploy-lag watcher never reads the landing time in CI (row 9)

- f396f2ba8 (SPL-3653, 10-27) made the lag age run from the push that landed
  a commit (`_spl_lag_landed_at`,
  `csi-spl-orc/src/bash/run/check-deploy-lag.func.sh:203-216`), read with
  `gh api repos/{owner}/{repo}/activity`. When that call fails, the age
  falls back to the commit time and says so: `age_from=commit:gh-api-failed`.
- The wf 00 step that runs it gives `gh` no token:
  `.github/workflows/00_deploy-lag-watch.yml:217-224`, env `ENV`, `SHA`,
  `GRACE_MINUTES` only; the one `GH_TOKEN` in the file (line 155) belongs to
  the `watch` job's dispatch step. `grep -c 'age_from=commit:gh-api-failed'`
  over the 6 lag job logs of row 9 -> `0 0 1 1 1 1`: the two zeros are the
  run of 10-26 19:24, before f396f2ba8; the 4 jobs after it all fell back
  (runs 40488667324, 40585570378, 40644208221).
- Effect: every lag verdict measures from the author's commit time, which is
  earlier than the push, so a hub roll that takes the usual ~45 min crosses
  the 45 min grace (`age=45m`, `46m`, `50m` in those logs) and the hourly
  watcher goes red.
- Smell: **the action is tested only with a gh stub** (`GH_STUB_JSON` in
  `csi-spl-orc/src/bash/tests/check-deploy-lag.tst.sh:127-144`); nothing
  checks that the workflow step can reach the real API, and the fallback is
  silent apart from the `age_from` word.

### 3.2 The daily backup check runs inside the backup window (row 21)

- `csi-spl-utl/src/bash/run/cloud-sql-backup-verify.func.sh:153,180-184`
  reads only `.[0]`, the newest backup, and any status other than
  `SUCCESSFUL` is an ALERT. Its test pins that on purpose
  (`csi-spl-utl/src/bash/tests/cloud-sql-backup-verify.tst.sh:200-205`,
  case 5: RUNNING -> ALERT).
- The schedule is `17 3 * * *` (`.github/workflows/45_db-backup.yml:76`). The
  instance's backup window starts at 01:00 UTC
  (`csi-spl-iac/src/terraform/040-cloud-sql-postgres/03-cloud-sql.tf:61`).
  On 10-26 and 10-27 the automated backup started at 03:38:33Z and
  03:35:28Z, minutes after the check began, so the newest backup was
  `RUNNING` with `age_hours=0` (logs of runs 40264963172, 40444881296).
  10-25 and 10-28 were green.
- Smell: **a freshness check that cannot tell "in progress now, yesterday's
  is fine" from "broken"**, scheduled where the two overlap. 2 red runs in
  4 days, each a false alert.

### 3.3 The bundle budget is measured only in CI (row 2)

- The initial gzip budget (`ci_initial_gzip_kb`, 155 KB) is checked by
  `perf-budget.py bundle` in wf 10 only (`.github/workflows/10_ci-quality.yml:597-599`;
  `git grep -n 'perf-budget' origin/master -- csi-spl-iac/src/bash` -> only
  the `ci-build-once.tst.sh` contract test). The pre-push `wui-e2e` part
  already builds the same mock bundle (`_ppe_generate`,
  `csi-spl-iac/src/bash/run/check-pre-push-e2e.func.sh:264`) and never
  measures it.
- Cost on 10-27: the first red sha d4f00c4ba carries 840fdec0b (German blog
  locale; `git merge-base --is-ancestor 840fdec0b d4f00c4ba` -> true), which
  took the entry chunk to 155.1 KB; 8 red runs and 9 red jobs over 75
  minutes until 31559e80c moved the chime synth to a lazy chunk. Every lane
  that pushed in that window inherited the red.
- Smell: **a gate whose input is built on the box but whose check exists only
  in CI.**

### 3.4 The pre-push e2e pick does not follow a layout change to the phone tests (rows 1, 19)

- 46afd70ba (SPL-3785) changed `src/layouts/default.vue` and `main.css` for
  every phone level. Four e2e files outside its own commit went red
  (`mobile-stack`, `command-palette`, `omnibox-grip` and the snackbar case):
  10 red runs, 24 red jobs, fixed only by two test commits 8b3bcbc52 and
  687b0e50d.
- The pre-push pick (since e87062a26, SPL-3612) scores test files by the
  `data-test` / testid strings of the changed file and of its users
  (`_ppe_keys`, `_ppe_names`, `_ppe_closure`,
  `check-pre-push-e2e.func.sh:110-160`). A layout has no users by name
  (line 120 returns nothing for `src/layouts/*`), and the phone tests select
  by attributes such as `data-mobile-level` (`mobile-stack.test.mjs:126`,
  `command-palette.test.mjs:275`), which are not testids.
- **Measured by the agy seat** (seat file section 3.1; the editor did not
  re-run it). `_ppe_select` on 46afd70ba's diff (`main.css`,
  `ChannelSidebar.vue`, `layouts/default.vue`, `pages/issues.vue`) keeps 6
  files and CUTS all four that went red in CI: `omnibox-grip` (score 31),
  `command-palette` (25), `mobile-stack` (22), `undo-snackbar-mobile` (3).
  Three causes: the case pattern at `check-pre-push-e2e.func.sh:80` has no
  `*.css` (the editor read the line again and confirmed it), line 120 skips
  `src/layouts/*`, and `_ppe_keys` (line 110) reads only `data-test` /
  `testId`. Still unknown: whether 46afd70ba's lane ran the e2e part.
- Smell: **a test selector that keys on one kind of hook (testids) while
  the tests most coupled to a shared file key on another (state attributes).**

### 3.5 The hub exits on its first failed Cloud SQL dial (row 13)

- The dev revision `csi-spl-hub-dev-01128-muv` of 10-28 (wf 20 run
  40640625433) logged, at 06:13:57Z: `Cloud SQL connection failed ... dial
  error: ... timed out after 10s`, then `spool: ping postgres: failed to
  connect ... connection refused`, then `Container called exit(1)`, then
  `failed the configured startup probe checks`. Command, read-only, as the
  dev project SA: `gcloud logging read
  'resource.type=cloud_run_revision AND
  resource.labels.revision_name=csi-spl-hub-dev-01128-muv' --project
  csi-spl-dev --freshness=3d`. The agy seat's trace (6 checks, ~90 s,
  rollback) is the guard's side of the same event.
- The hub opens the store once: `openStore` (`csi-spl-api/src/go/spool-hub-api/cmd/spool/hub.go:690-695`)
  calls `store.OpenPostgres`, which does one `pool.Ping` and returns the
  error (`internal/store/postgres.go:111-114`). There is no retry. The
  startup probe allows 120 s (`period_seconds = 1`, `failure_threshold =
  120`, `csi-spl-iac/src/terraform/030-cloud-run-hub/04-cloud-run-service.tf:117-125`),
  but the process exits after the 10 s dial timeout and wastes the other
  110 s.
- It is not a one-off. `textPayload:"Cloud SQL connection failed"` on
  `csi-spl-hub-dev` over the last 7 days -> 47 lines on 10 revisions
  (00825-sun 21, 00828-lit 14, and 1 or 2 each on 01053, 01090, 01096,
  01099, 01102, 01111, 01128, 01174; `--limit 50`, 47 lines, so the limit did
  not cap the count). Among the 100 failed runs only 01128 matches a red
  wf 20 run. Why the other revisions still became Ready is unchecked. The
  editor did not check prd.
- Smell: **a fatal one-shot dial at boot, in front of a connector that
  times out now and then**, with a start budget 12x longer than the dial
  timeout.
- `postgres.go` has a live 2-line edit in lane g-523 (`lane-map.sh --check`
  exit 3), so F5 changes only `hub.go`.
