What paid off most per hour of lane time, in order: **round-trip removal on the DB path** (N+1, batch, CTE, RETURNING, pipelining: every row held, n=5, deterministic), **CI parallelism** (C2, C4: minutes per push), **one-pass encoders with a golden + fuzz guard** (G9), **removing forced layouts at mount** (W3, W5). What did not: caches that the real path overrides (G11 plan, C5 wf50), and a predicted /N gain that a bench of the whole path would have shown as -16 % (G8).

**The biggest gap round 4 never looked at was the live database.** Every r4 DB number came from a private Postgres behind a counting proxy. The live read in section 2.4 shows that one background sweep holds 28.4 % of prd DB time, and one PUT route deadlocks 47 times a day. Neither can be seen in a round-trip count.

## 1. Rules for every lane

- Measured on trunk `751ccd61` (v8.9.8). Every site carries its cost now, with n. Before the change, re-measure on your rebased trunk with the row's method; a change that shows no gain is dropped and reported, never shipped.
- The 30 rows' files are pairwise disjoint and off every live lane at planning time (`lane-map.sh --check` on the 49 existing paths of section 3: rc 0, free, 2026-10-04 ~22:40Z; `.github/workflows/20_hub-build-deploy.yml` answered rc 3, held by c-221@sat, so it is not in the plan; local worktrees' own commits touch none of them). Off migrations, `msg/msg.go`, `store/fleet_*.go` and the rotation/lease/spawn/desk scripts. A lane touches only its row's files plus new test files beside them.
- One commit per site, with before/after and n in the message.
- Live DB and hub rows prove the gain on dev AND prd with the same read-only action before and after the roll (section 2.4). Lab ratios (proxy RT, bench) are the gate before the push; the live number is the result.
- Done means: on master through the pre-push gate; hub or WUI runtime changes deployed to dev AND prd with the served version checked (hub `/version`, WUI `build.json`); before/after numbers with n; report to the orchestrator on task `7d7e86a9-078f-4c8a-9a44-d6e18d2db2f7`.
- GCP: per-environment service-account keys only, never the owner account. Live measurements are read-only.
- Box: `satellite` = the satellite box (Chrome, lower load: WUI timing rows); `main` = the main box (it holds both env SA keys, so live before/after reads run there; also the ssh-to-satellite row); `either`.

## 5. Measured and not proposed

Each of these was measured; none is a row, for the reason given.

- **Hub CPU, memory, instance size.** CPU per-minute p99 max 0.04 (prd 24 h) / 0.11 (7 d), memory p99 <= 0.25. Fractional CPU forces concurrency 1 on a WebSocket hub, so the only lever is cost, which is the owner's call (spec 047), not a performance item.
- **Cloud SQL tier and connections.** DB CPU p50 0.13 (max 0.61, 7 d), 138 MB fully cached, backends p95 12 / max 21 of 25. Do not raise the hub pool (8) without lowering the other users first. Rows E01, E03, E04 and E17 take DB time off; a bigger tier would hide it.
- **`work_mem` 4 MB vs temp_files 614 / 4.2 GB since 2026-09-18 (prd).** Which statement spills is unknown (`log_temp_files` is off). It needs a Cloud SQL flag change (terraform 040, owner go) before it can be measured.
- **`messages_search` GIN (12 MB, idx_scan 0 since 2026-09-18) and the redundant `messages_channel` index (covered by `messages_channel_stats`).** Real write costs, and /v1/view/search is slow (prd p50 716 ms, n=2; dev p50 144 / p95 457 ms, n=98), but both are migrations: give them to a migration lane with this evidence.
- **Revision churn**: ~41 hub revisions a day, 244 prd container starts in 7 d; each drops every socket. A release-cadence question, not code.
- **wf20 deploy job** (~60 s of SDK setup, Go setup, registry check and migrate-binary build after the suite, n=12): `.github/workflows/20_hub-build-deploy.yml` is held by c-221@sat (hub autoheal) at planning time. Next round, or that lane.
- **wf10 self-hosted runner queue** 162 s median before the first job (n=20; hosted wf11 queues 3 s): runner capacity, not code.
- **wf50 compose build** (111 s, n=20): r4 measured a buildx cache as slower (119 vs 101.5 s); the layers change on every sha.
- **r4 W8** (defer the notify / error-journal plugins): 0 bytes can leave the initial chunk while `app.vue` and three stores import them statically.
- **r4 W1 site 2** (`channel-feed.mjs` orderChannels / orderPeers): 0.0 ms in all 10 profiles; code-unit compare is no faster once ICU is warm (n=12).
- **MessageComposer dock reads** (`MessageComposer.vue:430,466`: 23.9 + 25.1 + 9.2 ms forced style/layout on the phone, n=5): a real cost, but the composer dock has been one lane's file since round 4 and was touched 6.4 h before planning. Hand the numbers to its owner.
