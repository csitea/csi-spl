## 2. Practices (34)

**System and architectural**
1. Event-driven over polling: a poll is only a backstop.
2. Poll cadence matches the deadline it serves.
3. An incremental checkpoint plus a periodic full reconcile.
4. A maintained projection (heads, counters) with a drift oracle.
5. A conditional read (validator, 304) before the data reads.
6. Invalidate narrowly: a cache key covers only what the view reads.
7. Keep a long operational check off the hot pool, and off the deploy path.
8. Bound every long read with a statement timeout or budget.
9. Measure, then drop. A row with no measured gain is written down as dropped.

**Database**
10. Set-based over per-item statements (`= ANY($n)` beats N lookups).
11. A set anti-join over a per-row correlated `EXISTS`.
12. Push the top-N into each arm of a `UNION`.
13. A list projects only the columns it paints; wide text stays on the one-row read.
14. Keyset pagination over windowing the whole table.
15. A covering index, so the scan is index-only (landed: `messages_channel_stats`).
16. Autovacuum insert scale keeps index-only scans index-only (landed: ap-04).
17. An incremental add stays O(index probes) and never rescans its topic.
18. A deferred trigger keeps its work small and its locks last.
19. On a micro, the pages a statement touches matter more than how clever its plan is.
20. Do not trust row estimates under FORCE RLS: the estimate is checked by EXPLAIN ANALYZE.
21. Forward-only, idempotent migrations with `lock_timeout`.
22. A write that changes nothing writes nothing (a conditional UPSERT).

**API and Go**
23. Batch one request's or one tick's reads into one round trip (`queryTenantBatch`).
24. Scope plus statement in one batch (landed: `tenantBatch`, `rls.go`).
25. Memoise a repeated read within one request (landed: G1).
26. Encode a fan-out frame once (landed: G8).
27. Typed structs over `map[string]any` on hot frames (landed: G12).
28. Pool response buffers (landed: G10).
29. Fold the follow-up read into the write with `RETURNING` (landed: G6).
30. One CTE instead of lock, then read, then update (landed: G5).

**Code quality**
31. One home for a business predicate. A rule pasted into several statements drifts.
32. A config knob per deadline, not one tick for everything.
33. Every claim about speed has a counting test or a bench that guards it.
34. Report the warm plan and the production mean side by side. They answer different questions.

### 4.1 Relay tick: each sweep at the cadence of its deadline, one set read per tenant

Practices 1, 2, 10, 23, 32.

Files: `csi-spl-api/src/go/spool-hub-api/internal/hub/relay.go:60` (`Relay`, run
every `QueueRelay`), `:86` (`UnheardPosts`), `:103`, then `:122` (`UnansweredPosts`)
and `:152` (`ReescalatablePosts`). Store: `store/postgres.go:565` (`QueuedFor`),
`store/acks.go:61` (`UnackedFor`), `store/fallback_postgres.go:80/111/143`.
Config: `config/config.go:325` `QueueRelay` default `5s`, `:346` `ReescalateEvery`
`120s`, `UnansweredGrace` `120s`; `hub/commit.go:22` `ackTimeout = 60 * time.Second`.

Now: every 5 s each hub process runs `QueuedFor` and `UnackedFor` once per held
box socket, then the three fallback sweeps once per tenant. Per day:
389 766 + 387 958 + 3 x 155 453 = **1 244 083 statements, 34.9 % of the
3 561 168 in the window**, for 85 236 ms (8.2 %). Each one also carries a
`set_config` in its batch, which accounts for about 1.24 M of the 1.92 M
`set_config` calls (about 12 s more). That totals about 97 s/day (9.3 %),
the same size as `countsRead`. The deadlines these polls serve are 120 s
(unanswered), 120 s (re-escalate) and 60 s (unacked). Queued rows already
arrive by LISTEN/NOTIFY: `Wake` defaults to `true` at `config/config.go:329`,
and the comment says "not at the next QueueRelay tick". So the 5 s poll is
oversampling: 24 x for the 120 s sweeps, 12 x for unacked.

Change:
- The unanswered and re-escalate sweeps run every 30 s, a tick counter in `Relay`.
- `pushUnacked` runs every 15 s.
- `QueuedFor` and `UnheardPosts` keep the 5 s backstop, but run as ONE
  `to_box = ANY($2)` read per tenant instead of one read per box.
- One `queryTenantBatch` per tenant per tick.
- The SQL predicates do not change.

Expected gain: the per-day statement count falls from 1.24 M to about 0.25 M
(the sweeps by 5/6, unacked by 2/3, queued from about 22 per tick (387 958 / 17 280 ticks) to one per
tenant). Re-escalate plus unanswered alone: 5/6 of 54 668 ms, about 45 s/day.
Escalation gets up to 25 s later against a 120 s grace. No screen gets faster:
this is DB CPU, statement overhead, and 4-connection pool occupancy.

For: the call counts above (n = one 24 h window, 3.56 M statements). The
deadlines are in the config. Wake is on by default.

Against: c2 disagreed with g1 5.10 (batching the same three reads) because
each read is sub-ms and no screen waits. This action is not that batch: it
removes about 1 M statements a day, and the batch is only its last bullet. The
risk is a missed wake: a queued row then waits up to 5 s, as it does today. An
unacked row waits up to 15 s more.

Proof:
- Insights calls for the five statements, n >= one 24 h window before and after.
- The relay tests on the fake clock, extended so a post still escalates within
  grace + 30 s.
- Prd escalation latency (fallback `delivered_at` minus `received_at`) p50 and p95,
  before and after.
- Drop the cadence part if escalation p95 moves by more than 30 s.

### 4.4 Channel GET: make the existing 304 gate reachable, before building a counter

Practices 5, 6.

Files: `csi-spl-api/src/go/spool-hub-api/internal/hub/view_stamp.go:43`
(`stampGate`), `hub/view.go:53` (channels is a `stampedView`),
`store/change_stamp.go:37` (`changeStampSQL`),
`csi-spl-rdb/src/sql/postgres/spool-hub/0103_tenant_change_stamps.sql:123`
(the `deliveries` trigger), and the WUI `csi-spl-wui/src/utils/spool-client.mjs:551`.

Now: one channel GET runs four statements, each 6 840 times a day: counts
14.02 ms, hidden-unread 2.91, marks 1.19 and subscriptions 0.32. That is
18.44 ms per GET and about 126 s/day (12.1 %), the biggest route cost.
R2-5 should answer an unchanged repeat with 304 after one stamp read. But
`changeStampSQL` (`FROM tenant_change_stamps WHERE tenant_id = $1`) is in
none of the 59 statements Insights holds for the window. So **no conditional
read reached the gate in 24 h** (`stampGate` reads the stamp whenever
`If-None-Match` is present). Two causes, both unproven:
- The browser never sends a validator. The WUI fetch sets none, so it relies on
  the HTTP cache, and the `read=<ch>~<cursor>` query changes the URL whenever a
  mark moves.
- The stamp never settles. Every `deliveries` write bumps the tenant stamp
  (0103:123). Bumps run 23 253 + 18 591 = 41 844 a day against 6 840 GETs.
  `countsRead` reads no `deliveries`
  (`sed -n 355,420p store/channels_postgres.go | grep -c deliveries` -> 0).

Change:
1. Measure first: count GETs that carry `If-None-Match`, and the share answered 304.
2. If the browser sends none, the WUI sends the last ETag it got for that path
   (an `If-None-Match` it holds itself), or drops the cursor from the URL when
   the server already holds the mark.
3. If the stamp churns, the channels view gets a stamp that omits `deliveries`.
   That is a second slot family in 0103, or a per-view trigger set.

Expected gain: the share of GETs that are unchanged repeats, times 18.44 ms,
up to about 126 s/day. No write-path cost, unlike g1 5.3's counter.

For: the gate is built and tested. The Insights evidence says it never runs.

Against: if real changes move the stamp between most GETs (1 306 inserts a
day plus read marks), the hit rate stays low. Then drop this row and take
g1 5.3. One more fact to check first: Insights may fold a statement it saw
only rarely into another row.

Proof: a hub log count of `If-None-Match` and 304 on `GET /v1/view/channels`
(n >= 24 h). Then the Insights calls of `countsRead` against the GET count,
before and after. Drop if the 304 share is below 20 %.

## 5. Not worth doing, and why

- **Box hello UPSERT** (135 886 x 0.32 ms = 43 488 ms, 4.2 %). It runs once
  every `defaultPresenceEvery = 30 * time.Second` (`hub/presence.go:24`) per
  box socket, so about 47 live sockets. A presence TTL of `2 x` that is what
  marks a half-open box offline. Halving the rate saves about 22 s/day but
  doubles the time a dead box looks online. No screen waits on it. g1 and the
  2026-10-06 plan dropped it too.
- **`set_config` campaign** (1.92 M x 0.01 ms). The scope already rides in the
  same batch as its statement (`rls.go` `scopeBatch`), so it costs no extra
  round trip. Action 4.1 removes about 1 M of these calls as a side effect.
- **`TenantsMissingPublicNotice`** (86 x 68.95 ms = 5.9 s/day). The
  function is `IMMUTABLE` (`grep -n IMMUTABLE 0173*.sql`), so it is not a
  volatility trap. 0.6 % is too small for a lane.
- **One home for the "signed human post" predicate** (practice 31).
  `grep -c "from_box = 'box-wui' AND m.from_id LIKE 'HUM-%'" store/*.go` -> 3
  in the store, plus the orc sweep's copy. This is a real drift risk, but it has
  no measured speed gain and no recorded incident, so by the owner's rule it is
  not worth a lane this round. Fold it into action 4.1's lane only if that lane
  touches all three statements anyway.
- **m1's ten** (ap-01a/b, ap-02, ap-04, ap-05, ap-07, ap-08, R2-1, R2-2,
  flow-scope, ap-03). Each one is landed, live, dropped or self-refuted. Its
  numbers predate `0fd227cd9`: flow counts are 9.09 ms here, not 77. That
  agrees with c2's review.
- **a1 #1-#4.** These are the dropped ap-06, ap-08, ap-03 and ap-09. a1 #2
  cannot work: the 0135 trigger is BEFORE, so `search_tsv` is not computed yet
  (c2). Flow-count debounce: the route p50 is already 4 ms after `0fd227cd9`,
  and no burst was measured.
- **a1 #6-#9** (merge frames, `fileRefs` in search, `withoutAgent`): no measured
  cost. Search is 6 calls a day in g1's window. **a1 #10** is CI, which is
  outside a DB and API round.
- **g1 5.7 (release-day scalar)**: c2 shows it is an index range already
  (`release_notes_released_at`, 0177). **g1 5.10 (relay batch alone)**: two
  sub-ms round trips; action 4.1 is the version of it with a measured gain.
- **`synchronous_commit` off, enabling `pg_stat_statements`, read replicas**:
  the first trades durability, the second restarts the instance (an owner
  call), and the third is not needed while the DB is 1.2 % busy (section 1).
