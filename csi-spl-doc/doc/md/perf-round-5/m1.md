## 2. Proposed Actions (10 Most Beneficial)

### 1. Flow counts: Seek on stored place/time (ap-01b)
- **Why**: Flow counts probe every event a member ever got (~3,530 for HUM-10), even if already read. This is O(all events), not O(unread).
- **Change**: Store `place_key` (`ch:<c>`, `dm:<id>[@box]`) and `cov_at` (message `received_at`) on each `flow_events` row. Seek on the stored place/time to read only events after each mark.
- **Best Practices**: CQRS, Event Sourcing, Covering Indexes.
- **Gain**: 77 ms -> <10 ms per call; ~-800 s/day (92% of 865.5 s).
- **Proof**:  
  - Before/after: Insights mean of `WITH fc` (n=11,229).
  - Result md5: Old vs. new on prd/dev (n=all members).
  - Postgres test: `FlowRead` equals today’s statement.
- **Files**: `flow_postgres.go`, migration `0136_flow_events_place_key.sql`.
- **Risk**: Medium (DDL on prd; deploy order DDL before hub).

---

### 2. Channel list: Filter archived lines by mark (ap-02)
- **Why**: The hidden-unread query expands all 4,849 archived lines on every call, then drops them for readers whose marks cover every channel (HUM-10: 0 rows out, 25-36 ms).
- **Change**: Expand archived lines only for channels the reader has no mark on.
- **Best Practices**: Lazy Loading, Index-Only Scans.
- **Gain**: 26 ms -> ~2 ms per call for all-marked readers; ~-280 s/day (91% of 308.4 s).
- **Proof**:  
  - Before/after: EXPLAIN for HUM-10 (0 rows out) and a no-mark reader (n=3).
  - Insights mean of `hiddenUnreadRead` (n=11,734).
  - Route p50/p95: GET `/v1/view/channels` (24h).
- **Files**: `channels_postgres.go` (`hiddenUnreadRead`).
- **Risk**: Low (behaviour unchanged for readers with no marks).

---

### 3. Messages autovacuum: Tune for index-only scans (ap-04)
- **Why**: The channel counts statement visits the heap for 3,691 of 6,917 index-only rows (visibility map lag).
- **Change**: `ALTER TABLE messages SET (autovacuum_vacuum_insert_scale_factor = 0.02, autovacuum_vacuum_insert_threshold = 200)`.
- **Best Practices**: Data Locality, Batch Index Updates.
- **Gain**: 17-22 ms -> ~10-12 ms per call; ~-100 s/day (39% of 256.2 s).
- **Proof**:  
  - Before/after: EXPLAIN (Heap Fetches -> near 0 after autovacuum, n=3).
  - `do_spl_db_health SECTION=vacuum`.
- **Files**: Migration `0137_messages_autovacuum.sql`.
- **Risk**: Low (prd DDL; more autovacuum runs on micro instance).

---

### 4. Topic walk: Server-maintained topic summary (ap-07)
- **Why**: Topic lists walk ~45 messages per listed topic (2,301 for 51 DM topics). Each candidate step rescans ~370 archived cards (archived OR cannot use its index).
- **Change**: Keep one "topic head" row per topic (latest line, channel/DM, parties, subject), upserted in the send’s INSERT CTE.
- **Best Practices**: Materialized Views, Immutable Data.
- **Gain**: Walk work -80-90%; ~-200 s/day (90% of 187.1 s).
- **Proof**:  
  - Before/after: ap-00 hot-measure walk_dm/walk_all (n=20).
  - Route p50/p95: GET `/v1/view/topics` per shape (24h).
- **Files**: Migration + trigger, `view_postgres.go` (`viewTopicsSQL`).
- **Risk**: High (insert-path trigger, backfill, prd DDL).

---

### 5. WUI: Fix channels GET per PUT (echo fix) (ap-05)
- **Why**: The WUI sends one GET `/v1/view/channels` per read-mark PUT (4,670 vs. 4,817 in 8.4h). The cause: an echo at the same timestamp that only fills in the empty message id is judged "later" by `laterThan`.
- **Change**: An echo at the same time that only fills in the empty message id is not a new mark.
- **Best Practices**: Idempotency, Delta Sync.
- **Gain**: ~-600 s/day (100% of 602.6 s).
- **Proof**:  
  - Before/after: Dev browser network log (n=20 PUTs: channels GETs per PUT).
  - Prd route n: GET `/v1/view/channels` (24h).
- **Files**: `read-sync.mjs` (`mergeMarks` / `laterThan`).
- **Risk**: Medium (stale channel badge if the keys push does not cover a case).

---

### 6. Message insert: Batch Flow event updates (ap-08)
- **Why**: A message insert takes 46-86 ms (n=837/day). The Flow-candidate CTE (`flowInsertCTE`) is a named suspect.
- **Change**: Batch Flow event updates in the insert’s `WITH ins AS (INSERT ...)` CTE.
- **Best Practices**: Write-Ahead Logging, Batch Processing.
- **Gain**: ~-20 s/day (41% of 48.3 s).
- **Proof**:  
  - Before/after: Lab pg16 `EXPLAIN (ANALYZE, BUFFERS, WAL)` (n=20).
  - Insights mean of message insert (n=837).
- **Files**: `flow_postgres.go` (`flowInsertCTE`).
- **Risk**: Low (behaviour unchanged).

---

### 7. WS compression: Permessage-deflate (R2-1)
- **Why**: WS `message` frames are 707 B per tab, with no compression. Browsers negotiate permessage-deflate on their own.
- **Change**: Set `AcceptOptions.CompressionMode = websocket.CompressionContextTakeover`.
- **Best Practices**: Compression.
- **Gain**: 707 B -> ~166 B per frame (-76%).
- **Proof**:  
  - Before/after: Simulated over n=40 real 192 B bodies (spec 059).
  - RSS: Measure with N tabs (choose mode by memory).
- **Files**: `wui.go` (`AcceptOptions.CompressionMode`).
- **Risk**: Low (context takeover keeps one flate state per socket).

---

### 8. Reconnect: Delta catch-up (`since=<cursor>`) (R2-2)
- **Why**: On reconnect, the WUI re-reads a whole channel page (~44 KB JSON / ~6 KB gzip, ~13 ms DB per tab), even when nothing was missed.
- **Change**: Add `since=<cursor>` to the topics list. Fall back to the full page after a long gap.
- **Best Practices**: Delta Sync.
- **Gain**: ~-44 KB per tab per reconnect.
- **Proof**:  
  - Before/after: Dev network log (n=3 reconnects).
  - Hub test: N wakes inside window -> 1 push with final counts.
- **Files**: `view.go` (topics handler), `spool-client.mjs` (`catchUp`).
- **Risk**: Low (edits/moves/reactions need a path).

---

### 9. Flow counts: Scope to tenant (JIT/generic plan) (flow-scope)
- **Why**: `FlowRead` and `FlowFanout` run under plain `pgScopeTenant` (plan cache auto, JIT on). No A/B reproduced a slowdown, but the hub’s Insights mean (77 ms) suggests the good shape is already used.
- **Change**: If a generic plan or JIT is slower, scope to tenant before the Flow counts.
- **Best Practices**: Query Plan Caching.
- **Gain**: ~-30 s/day (3% of 865.5 s).
- **Proof**:  
  - Before/after: `ENV=prd TENANT_ID=t1 READER=HUM-10 MEASURE_N=20 MEASURE_JIT=both MEASURE_PLAN_CACHE=auto ./run -a do_spl_db_hot_measure` vs. `MEASURE_PLAN_CACHE=force_custom_plan`.
- **Files**: `rls.go`, `flow_postgres.go`.
- **Risk**: Low (one-line scope commit).

---

### 10. Topic walk: Split archived OR into two probes (ap-03)
- **Why**: The archived check is an OR that cannot use its index. Splitting it into two NOT EXISTS probes stops reading ~370 archived cards per candidate.
- **Change**: Check "is this topic archived" with two index probes instead of one OR.
- **Best Practices**: Avoid N+1 Queries.
- **Gain**: ~-50 s/day (27% of 187.1 s).
- **Proof**:  
  - Before/after: ap-00 hot-measure walk_dm/walk_all (n=20).
  - Route p50/p95: GET `/v1/view/topics` per shape (24h).
- **Files**: `topic_archive_postgres.go` (`archivedTopicHideSQL`).
- **Risk**: Medium (planner-shape sensitive).
