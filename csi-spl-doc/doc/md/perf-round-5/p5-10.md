# P5-10 steps 1+2: the channels GET 304 gate made reachable (SPL-1740)

Row 10 of [the round 5 plan](../perf-round-5-plan.md). Steps 1 and 2 only;
step 3 (the maintained counter) is decided on the 304 share measured here.

## 1. What changed

| part | change | file |
|---|---|---|
| step 1, log | every `GET /v1/view/channels` logs one `view_stamp_cond` line: `inm` = what the request held (`none`, `stamp` = a stamp tag, `body` = a body-hash tag) and `gate` = what the gate did (`304` = answered before any data read, `minted` = a stamp tag rides the 200, `unsettled`, `none` = no tag held, `error`). The wire status, a body-hash 304 included, is the request log's | `csi-spl-api/.../internal/hub/view_stamp.go` |
| step 2, stamp | a second stamp, `n_nodeliv` / `nodeliv_changed_at`, moved by every covered write except `deliveries`; the channels view gates on it. One stamp read still answers both | `csi-spl-rdb/.../0190_change_stamp_no_deliveries.sql`, `internal/store/change_stamp.go` |
| step 2, client | the WUI holds the ETag and body of its last channels 200 per path (8 at most) and sends `If-None-Match` itself; a 304 returns a copy of the held body | `csi-spl-wui/src/utils/spool-client.mjs` |
| step 2, CORS | the view preflight allows `If-None-Match`; view answers expose `ETag` | `internal/hub/view.go` |

Cost: a WUI channels read now carries a non-safelisted header, so a NEW
channels URL (another `read=` mark set) pays one preflight, cached 2 h per URL
(`corsMaxAge`). A repeat of the same URL pays none.

## 4. Read marks that move nothing write nothing (SPL-1761)

The WUI re-sends a member's marks every 5 s and on tab hide
(`csi-spl-wui/src/utils/read-sync.mjs`), most of them unchanged. The upsert
in `SaveReadMarks` (`internal/store/read_marks.go`) took the newer of each
pair but still UPDATEd the row (`updated_at`), so the `read_marks` change
stamp trigger (rdb 0103) fired on every re-send and both stamps stayed
unsettled.

| part | change |
|---|---|
| Postgres | `ON CONFLICT ... DO UPDATE ... WHERE` the mark advances (`(at, msg_id)` later) or `seen` rises: a re-send that moves nothing updates no row, fires no trigger, and sends no `spool_wui` wake |
| memory | the same: an unchanged key is not written and no wake is sent |
| test | `TestReadMarksUnchangedResendKeepsStamp`, both drivers: an unchanged and an older re-send leave both stamps where they were; an advancing mark, a higher `seen` and a new key move them (the control) |

Gate evidence (local, `postgres:16-alpine`, before the fix, n = 1 write
each): the unchanged re-send moved both stamps 2 -> 3, the older re-send
3 -> 4. After the fix both stay, the three controls move.

The `updated_at` of an unchanged mark now keeps the time it last moved.
Its one reader, the `f:<msg_id>` sweep (`flowMarkSweepSQL`), compares it with
the sweep's own now, so an older value deletes nothing it would not have.

### 4.2 What still moves the narrow stamp (SPL-1812)

prd, read-only, tenant t1, 2026-10-14 07:39:10..08:41:22 UTC (62.2 min).
Method: 53 snapshots of `pg_stat_user_tables` for the 0103 covered tables
plus `sum(n), sum(n_nodeliv)` of `tenant_change_stamps` (rdb 0190), one per
~45 s until 08:24Z and one closing snapshot; the timestamp columns of the
same window for who wrote; the `view_stamp_cond` lines for the gate.

The narrow stamp `n_nodeliv` moved **324 times** (~313/h). A transaction
bumps it once however many covered rows it writes, so the table below
counts row writes per source, not bumps (DB-wide counters; t1 is nearly
all of the traffic).

| source (covered table) | row writes | t1 rows by timestamp column | read by the channels view? |
|---|---|---|---|
| `read_marks` | 206 (19 ins, 187 upd) | 32 rows: 27 `t:<topic>`, 5 `ch:` | only `ch:` marks |
| `messages` | 177 (171 ins, 6 upd) | 159: 75 in a channel, 84 with `channel IS NULL` (DMs, agent topics) | only `channel IS NOT NULL` |
| `channel_subscriptions` | 94 (47 ins, 47 upd) | one burst, 08:19..08:20Z | yes |
| `issues` | 38 (15 ins, 23 upd) | 18 | no |
| `tenant_memberships` | 6 | | yes (at the door) |
| `message_kind_changes` | 1 | | |

Per 45 s interval (52 intervals): the stamp stood still in 8. Most moving
intervals carried read_marks and messages writes together (117 bumps in 14
intervals); issues alone moved it in 2.

The `read_marks` writes are real advances (187 updates on ~32 rows, mostly
`t:<topic>` marks as a reader moves through topics), not the unchanged
re-sends SPL-1761 removed. PUT /v1/me/reads ran 684/h (06:39..07:39Z,
`do_spl_hub_route_latency`).

Gate, same window, n = 193 `view_stamp_cond` lines, hub revisions
00689..00692:

| `gate=304` | `unsettled` | `minted` | `none` |
|---|---|---|---|
| 22 (all `inm=stamp`) | 102 (81 `inm=body`, 21 `inm=stamp`) | 26 | 43 |

**Verdict: no single source dominates, and none has the SPL-1761 shape.**
read_marks (~40% of the row writes), messages (~35%) and issues (~7%) all
write something real. What they share: most of it is data the channels
view does not read (`t:` marks, messages outside a channel, issues), roughly
two thirds of the movers. Taking those out of the narrow stamp needs a
per-row rule in the trigger (`tenant_change_bump`: the table plus
`mark_key` / `channel`), which is a migration and not a small fix. So, as the
brief says, step 2 was not built; the choice between that narrowing and the
step 3 maintained counter is made on these numbers. n = 1 hour.
