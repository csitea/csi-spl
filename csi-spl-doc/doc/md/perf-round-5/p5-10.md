## 4. Read marks that move nothing write nothing (SPL-1761)

The WUI re-sends a member's marks every 5 s and on tab hide
(`csi-spl-wui/src/utils/read-sync.mjs`), most of them unchanged. The upsert
in `SaveReadMarks` (`internal/store/read_marks.go`) took the newer of each
pair but still UPDATEd the row (`updated_at`), so the `read_marks` change
stamp trigger (rdb 0103) fired on every re-send and both stamps stayed
unsettled.

| part | change |
|---|---|
| Postgres | `ON CONFLICT ... DO UPDATE ... WHERE` the mark advances (`(at, msg_id)` later) or `seen` rises: a re-send that moves nothing updates no row, fires no trigger, and sends no `spool_wui` wake |
| memory | the same: an unchanged key is not written and no wake is sent |
| test | `TestReadMarksUnchangedResendKeepsStamp`, both drivers: an unchanged and an older re-send leave both stamps where they were; an advancing mark, a higher `seen` and a new key move them (the control) |

Gate evidence (local, `postgres:16-alpine`, before the fix, n = 1 write
each): the unchanged re-send moved both stamps 2 -> 3, the older re-send
3 -> 4. After the fix both stay, the three controls move.

The `updated_at` of an unchanged mark now keeps the time it last moved.
Its one reader, the `f:<msg_id>` sweep (`flowMarkSweepSQL`), compares it with
the sweep's own now, so an older value deletes nothing it would not have.

|---|---|---|---|

**Verdict: no single source dominates, and none has the SPL-1761 shape.**

per-row rule in the trigger (`tenant_change_bump`: the table plus
`mark_key` / `channel`), which is a migration and not a small fix. So, as the
brief says, step 2 was not built; the choice between that narrowing and the
step 3 maintained counter is made on these numbers. n = 1 hour.

### 4.3 The narrow stamp moves only on rows the channels view reads (SPL-1831)

Owner pick A (HUM-10, t1 `eafc9b15`, answer msg `0a2d8570`): narrow the
stamp to what the channel list shows. rdb
`0196_change_stamp_narrow_channels.sql` gives the 0103 row trigger
(`tenant_change_bump`) a per-row rule for the narrow pair (`n_nodeliv`,
rdb 0190). The wide stamp `n` still moves on every covered write.

| covered row | moves `n_nodeliv` | why |
|---|---|---|
| `deliveries` | never | rdb 0190 |
| `issues` | never | the channels view reads no issues row |
| `messages` | in a channel, or archived (OLD or NEW side) | the archived-hide reads (`archivedHideSQL`, `hiddenLineSQL`) take archived cards of any channel, a topic root outside one included |
| `read_marks` `ch:` | always | the view's `mk` marks |
| `read_marks` `t:` | only when the topic has a line in a channel | `threadReadSQL`: a thread read elsewhere is not unread in its channel |
| `read_marks` `dm:` | never | not read by the view |
| every other covered table | always | as in rdb 0190 |

This is narrower than "no `t:` mark and no message outside a channel": the
channels view reads both in two places (`threadReadSQL` in
`markedUnreadRead`, the archived set in `hiddenUnreadRead`). Leaving them
out entirely would answer 304 over a changed unread count. A `t:` mark
written before its topic's first channel line is safe: that line's own
insert moves the stamp.

Test `TestChangeStampNarrowChannelRows` (Postgres, `postgres:16-alpine`,
n = 1 write per case): eleven writes, the wide stamp moves on each. Red
control: the same test on the schema without 0196 fails on exactly the five
"must not move" rows (a `t:` mark of a topic outside every channel, a `t:`
key that is not a uuid, a `dm:` mark, an issues write, a message outside a
channel; narrow stamp 20 -> 21 .. 24 -> 25). The six "must move" rows
(`ch:` mark, `t:` mark of a channel topic, a channel message, archiving a
line outside a channel, moving a line out of its channel,
`channel_subscriptions`) pass before and after.
`TestChangeStampNoDeliveriesEveryTable` now skips `issues` and the seeded DM
`messages` row; `TestReadMarksUnchangedResendKeepsStamp` uses `ch:` keys for
its "moves" controls.

One slot per transaction: with the per-row rule, one transaction often bumps
a tenant twice (a narrow-only row, then a whole one). With 0190's random
slot per bump, those two upserts locked two stamp rows in random order, and
two such transactions deadlocked: `TestTopicHeadRaceMirroredVsMerge`, 4 of
50 rounds `40P01` (pre-push full tier; the same suite on origin/master
`530da6e4f` passed). 0196 also replaces `tenant_change_bump_kind` to take
slot `txid_current() % 16`, the same for every bump of one transaction:
0 of 150 rounds after (`-count=3`).
