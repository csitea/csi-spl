## 2. Row-by-row review

### Row 01 — Wi-Fi power save: agree with changes

- `NetworkManager.conf(5)`, connection defaults: `wifi.powersave` "If left unspecified, the default value "ignore" will be used." The plan's "unconfigured (`default` = enabled)" is wrong: unset means NM leaves the driver's own setting (`iwlmvm power_scheme=2` on PC).
- `nm-settings-nmcli(5)` `802-11-wireless.powersave`: valid values `default (0), ignore (1), disable (2), enable (3)`. The plan's `[connection] wifi.powersave = 2` in a `conf.d` file is valid.
- Changes: (a) the verify command uses `iw`, not installed on PC: install it in the action, or verify with `nmcli -g 802-11-wireless.powersave` and NM's log. (b) Do not claim it fixes the drops: target = BEACON-LOSS and DISCONNECTED counts for 24 h before vs 24 h after, counted as in section 1. (c) It costs battery; acceptable on a mostly-mains laptop, but say it.

### Row 02 — connectivity check: agree with changes (the most valuable row)

- `NetworkManager.conf(5)` CONNECTIVITY SECTION: "default-route of devices without global connectivity get a penalty of +20000 to the route-metric". This one setting is the automatic switch the owner asked for: a Wi-Fi that is associated but has no internet loses its default route to any uplink that has internet.
- Same section: `interval` default 300 s; `timeout` "how long to wait for a response before connectivity is marked as limited … default is 20 seconds". With `interval = 10` and no `timeout`, detection is up to ~10 + 20 s. Set `timeout = 5` and state the target as <= interval + timeout (15 s).
- Same section: a strict `rp_filter` makes per-device checks fail on all but the best route. PC is loose (`2`) on `default` and on the Wi-Fi device, so new tether interfaces inherit loose. The action asserts `rp_filter != 1` on every uplink.
- Install `network-manager-config-connectivity-debian` (1.52.1-1) for the `uri`, and put only `interval` and `timeout` in the plan's `30-connectivity.conf`. `response` can go: its default is already `NetworkManager is online`.
- The check calls a Debian host every 10 s (~8640 requests/day). Fine for one box. Alternative: the hub's health endpoint (host from cnf `BASE_DOMAIN`, no literal), `response=` empty with a 204 — it also proves the hub is reachable, which is what the fence needs.

### Row 03 — wired takeover: agree

- `nm-settings-nmcli(5)` `connection.autoconnect-priority`: range -999..999; "this property only matters if there are more than one candidate profile to select for autoconnect". PC's wired profile is the only one for `enp0s31f6` and has `autoconnect yes`, so `-999` most likely does **not** stop it activating on carrier. The change is still right: it beats NM's auto-created "Wired connection N" defaults and any later profile.
- `ipv4.route-metric` default `-1` = "chosen automatically based on the device type". I believe, unchecked in the man page, that NM's automatic ethernet metric is already 100 (Wi-Fi measured 600 on PC). Setting 100 explicitly is harmless and makes the ladder readable.
- Proof = the real cable insert: `ip route show default` lists `enp0s31f6 … metric 100` first within 2 s.

### Row 04 — USB tether profile: disagree (as written)

- `match-device = interface-name:usb*,…` is a **`NetworkManager.conf(5)`** key (`[device]` / `[connection-*]` sections; its examples `match-device=interface-name:wlan0`, `match-device=type:wifi`). It is not a connection-profile key.
- The profile key is `nm-settings-nmcli(5)` `match.interface-name`: "A list of interface names to match. Each element is a shell wildcard pattern." In a keyfile (`nm-settings-keyfile(5)`) that is a `[match]` group, `interface-name=usb*;enx*;`. Leave `connection.interface-name` unset: it is an exact name.
- Metric 200 puts the phone's mobile data **above** Wi-Fi (600): whenever a phone stays cabled next to the laptop, all agent traffic (model calls, git, image pulls) moves to mobile data even with good Wi-Fi. Instead: tether `route-metric = 650` (below Wi-Fi) and `connection.metered = yes` (`nm-settings-nmcli(5)`: ternary, "the change takes effect immediately"). Failover still happens: a lost Wi-Fi removes its route; a Wi-Fi without internet gets +20000 from row 02.
- Corrected profile for the row lane:

```ini
[connection]
id=usb-tether
type=ethernet
autoconnect=yes
autoconnect-priority=50
metered=yes

[match]
interface-name=usb*;enx*;

[ipv4]
method=auto
route-metric=650

[ipv6]
method=auto
route-metric=650
```

- Caveat: `enx*` also matches any USB Ethernet dongle, which would then be metered at 650. Accept it, or narrow with `match.driver`; the tether driver names (I believe `rndis_host`, `cdc_ncm`, `cdc_ether`, `ipheth`, unchecked) are read by the lane from `/sys/class/net/<if>/device/driver` with a phone plugged in.

### Row 05 — Wi-Fi ladder: agree with changes

- One radio joins one SSID at a time, so per-SSID **route metrics never compete with each other**; only `connection.autoconnect-priority` picks which visible SSID is joined (`nm-settings-nmcli(5)`: "In case of equal priority, the profile used most recently is chosen"). Keep the priorities (10 / 8 / 7 / 5), drop the 600/700/710/750 metric ladder; Wi-Fi keeps its device default (600).
- Mark phone hotspot profiles `connection.metered = yes`.
- `autoconnect = no` on stale SSIDs: yes. The action never writes SSID names into the repo (hygiene): select profiles by UUID at runtime.
- With row 04 changed, the plan's ladder becomes "Wired 100 > Wi-Fi 600 (whichever SSID) > USB tether 650".

### Row 06 — WAN watchdog: disagree (replace it)

- The feature exists natively: `NetworkManager.conf(5)` connectivity section, the +20000 default-route penalty for a device without global connectivity (row 02). A second, home-made mechanism fights it.
- `ip route change … metric 1600` cannot work: `ip-route(8)`, "Key values (to, tos, preference and table) select the route"; `preference` is the metric, so a new metric is a new route. Adding a route and deleting NM's is undone by NM at the next DHCP renew or reapply.
- `NetworkManager-dispatcher(8)`: "For connectivity-change and dns-change it [the interface argument] is empty", and `CONNECTIVITY_STATE` is the global state. The script cannot learn "the dead interface" from that event.
- Same page: scripts "will be killed if they run for too long" — a 15 s probe loop in a dispatcher script is the wrong shape.
- Replacement: fold into row 02 (set `timeout`; prove the +20000 penalty appears in `ip route show default` while Wi-Fi is up but blackholed). The freed slot can take P1 below.

### Row 07 — DNS resilience: disagree (as written)

- `systemd-resolved` is not installed on PC; `/etc/resolv.conf` is a plain file NM writes. `FallbackDNS=` and `resolvectl flush-caches` do not apply. Installing resolved switches NM's DNS mode (`NetworkManager.conf(5)` `dns`: resolved is chosen automatically when `/etc/resolv.conf` is a symlink to its stub) — more change than this round needs.
- "DNS inside 32 Docker agent containers": no agent runs in a container on PC.
- The active Wi-Fi profile already pins `ipv4.dns = 8.8.8.8,1.1.1.1`, and NM writes them **before** the router's DHCP DNS. glibc waits `timeout` (default 5 s, `resolv.conf(5)`) per server, `attempts` default 2.
- Instead (one small row): the same `ipv4.dns` on every uplink profile (wired, tether, hotspots), plus `ipv4.dns-options = timeout:2,attempts:2` (`nm-settings-nmcli(5)` `ipv4.dns-options`: supported options include `attempts`, `rotate`, `timeout`). Proof: `getent hosts <api host>` on the host during the drill, < 1 s.
- `/etc/docker/daemon.json` `dns`: leave out. It needs a docker daemon restart, which stops the 14 containers (incl. test Postgres DBs other lanes use), for no agent benefit.

### Row 08 — beat continuity: agree with changes

- `csi-spl-orc/src/bash/run/spl-box-beat.func.sh` and `do_spl_box_beat` do not exist (`ls` -> No such file). The beat is `spl_wd_beat` in `spl_wd_fence`, `csi-spl-orc/src/bash/run/spl-watchdog.func.sh`, once per watchdog tick; `WD_TICK` default 30 s (`@param WD_TICK` in the same file).
- The fence fires after no ack for `box_down_min` (default 2 min, spec 102 10.2; read by `csi-spl-api/src/go/spool-hub-api/internal/hub/box_beat.go`). With a 30 s tick, a failover that ends within ~90 s never fences, with no code change.
- "Max beat gap < 25 s" contradicts the design: the gap is >= 30 s by construction. Target instead: beat ack age < `box_down_min` - `WD_TICK` (90 s) throughout the drill; 0 `FENCED` lines in the watchdog log.
- The poke (an early beat on a route change) is a fine refinement: the dispatcher touches a file, the watchdog's sleep wakes on it. That file is the watchdog's: the row lane runs `lane-map.sh --check csi-spl-orc/src/bash/run/spl-watchdog.func.sh` before editing.

### Row 09 — agent socket resilience: agree with changes

- `tcp(7)` `tcp_retries2`: "default value is 15, which corresponds to a duration of approximately between 13 to 30 minutes … The RFC 1122 specified minimum limit of 100 seconds is typically deemed too short." 6 is far below that floor.
- The plan's "~15-20 s" is wrong. I believe, from the kernel's `tcp_model_timeout()` in `net/ipv4/tcp_timer.c` (from memory, not checked against source on PC), that the give-up time is `(2^(n+1) - 1) x TCP_RTO_MIN` below the RTO cap, `TCP_RTO_MIN` = 200 ms (`tcp_rto_min_us` reads `200000` on PC): n=6 -> 127 x 0.2 s ~ 25 s; n=8 -> 511 x 0.2 s ~ 102 s, the first value above 100 s.
- 25 s is shorter than the 30 s re-scan seen in section 1: it kills healthy sockets (hub websocket, a long `git push`) that would have survived a blip. Use **`tcp_retries2 = 8`** at most, or keep 15.
- The fast path is `ss -K`; PC supports it (`CONFIG_INET_DIAG_DESTROY=y`; `ss(8)`: "-K, --kill Attempts to forcibly close sockets … silently skips sockets that the kernel does not support closing"). Kill by **source address**, not by port: on a default-route change, close TCP sockets whose local address is no longer on any interface or is not the new default's `src`. Old-source sockets are dead even when the old link stays up, because the kernel routes them out the new default with the old source address (see P1).
- The keepalive sysctls only affect sockets that set `SO_KEEPALIVE`; drop them or label them so.
- `http.lowSpeedLimit` / `http.lowSpeedTime`: valid (`git-config(1)`: "If the HTTP transfer speed, in bytes per second, is less than http.lowSpeedLimit for longer than http.lowSpeedTime seconds, the transfer is aborted"). HTTPS remotes only; SSH remotes need `ServerAliveInterval` / `ServerAliveCountMax` (`ssh_config(5)`, unchecked on PC). Set both.
- The dispatcher kill script: root-owned, not group/other-writable, not setuid (`NetworkManager-dispatcher(8)`), and short.

## 4. Proposals the plan missed (2)

### P1 — Keep live sockets on a link that is still up (source-based policy routing)

When a wired or tether link comes up while Wi-Fi stays up, every open socket keeps its Wi-Fi source address but is now routed out the new default, and dies; row 09 then has to kill it. Per-uplink policy routing keeps those sockets on the link they started on, so only sockets on a link that really went away need `ss -K`.

- Keys: `nm-settings-nmcli(5)` `ipv4.route-table` (each uplink's routes in its own table) and `ipv4.routing-rules` ("A comma separated list of routing rules for policy routing. The format is based on ip rule add syntax … routing rules in NetworkManager always need a fixed priority … only a number" for the table).
- Shape: each uplink profile gets its own table and a `from <its address> table N` rule; the main table keeps the metric ladder for new connections. Whether NM can bind a fixed rule to a DHCP address is unchecked: if not, the lane falls back to row 09's kill.
- Fits the slot freed by row 06.

### P2 — Count what we fix: one uplink event log

The plan's numbers (11 losses, 2 min 48 s) come from one hand probe. Add a dispatcher logger, a no-wait script (`NetworkManager-dispatcher(8)`: symlinked into `dispatcher.d/no-wait.d/`, run at once and in parallel), that appends `ts, action, device, CONNECTIVITY_STATE, default route` to a TSV, plus a read action `do_net_uplink_report` (events per day, outage seconds, fence lines). Rows 01, 02 and 10 then prove their targets from one file, with n, instead of each lane writing its own grep.
