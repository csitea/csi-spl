# CI volume: what the runs cost and where a push could run less (SPL-6385, 2026-11-24)

Owner HUM-10, t1 8acbaf69 (msgs a2ed77d7, 48761273, 6b2c484b): "are we
running too much cicd runs, are there any small changes which could get some
simple bypass cicd without having to do full e2e tests"; "first we need to
build the understanding and gather some empirical data". This page is the
data and a list of candidate actions. It decides nothing: the owner picks.

**Window**: runs created 2026-11-17T00:00Z..2026-11-23T23:59Z (7 full UTC
days), all branches. **Workflows read** at origin/master `ce30cb0c5`
(`.github/workflows` tree `9886e7d2c`; the last change to it, `e7e0dd768`).
13 commits changed `.github/workflows` inside the window, 6 of them wf 10 or
its classifier (`git log --since=2026-11-17 --until=2026-11-24 origin/master
-- .github/workflows | wc -l` -> 13); the numbers describe the files as they
ran, not as they read today.

**How** (read-only, no run touched):

- runs: `gh api repos/csitea/csi-spl/actions/runs?created=<3 h window>`,
  56 windows, each one's row count equal to its `total_count` (the API caps
  a filtered list at 1000) -> **10,698 runs**. `total_count` itself stops
  at 2,500 (a 7-day `event=push` query answers 2500, not 4,839), so check a
  window against it only when it holds fewer runs than that.
- runner minutes: the jobs of 1,047 runs (`/actions/runs/<id>/jobs`): **every**
  finished push run of wf 10 (451), wf 20 (114 push + 28 dispatch) and wf 30
  (123 + 1), and a random 15 of every other workflow and trigger (all of
  them where fewer ran). A job's billed minutes are its wall time rounded up
  to the minute (GitHub's rule); a workflow's total is its sampled mean x its
  run count.
- **Cross-check**: that estimate is **126,546** billed Linux minutes; GitHub's
  own billing for csi-spl over the same 7 days
  (`/organizations/csitea/settings/billing/usage?year=2026&month=11`, days
  17..23) is **126,908**. They agree within 0.3 %, so the per-workflow split
  below can be read as the real one.
- per push: the 673 push heads (one wf 25 run each, it has no path filter),
  in time order; a push's files are `git diff --no-renames --name-only
  <previous push head> <head>`.

### 1.5 The skipped runs

- All 4,024 skipped runs are **wf 12** (rerun a setup flake): it fires on the
  completion of each of 17 watched workflows and skips unless the run failed
  on attempt 1. A skipped run gets no runner (its job reads `skipped`, no

### 1.7 What the hourly full gate saw that the push gates did not

The 23 red hourly runs failed 23 (run, job) pairs: wui e2e 9, orc hermetic 9,
hub Postgres 2, orc features 1, iac 1, hub suite 1. For each, the two push
gates before and the two after that ran the same job:

- **16 of 23**: a push gate before or after was red in the same job: the
  hourly run saw a red the push gates already showed.
- **7 of 23** red only in the hourly run (11-17 08:45 hub pg, 11-18 21:45 orc,
  11-19 16:44 e2e, 11-20 01:44 orc features, 11-20 09:45 orc, 11-23 14:45 iac,
  11-23 15:45 hub). 6 of them did not repeat (the next hourly run was green,
  or red in another job): single reds, flake-shaped. One (11-20 09:45, orc
  hermetic) was red again at 10:45, and by then the push gates were red too:
  the hourly run saw that onset at most an hour early.
- n = 168 hourly runs in 7 days. This shows no persisting defect that **only**
  the hourly run caught in this week; it does not prove the backstop is never
  needed (a part-map miss is rare by design).
- The 14 hourly runs on the same head as the hourly run before all followed
  a **green** one (14 of 14): none was a re-check of a red.

### 1.7.1 What else the hourly run does

Finding reds is not its only job (`10_ci-quality.yml`, the `schedule:` and
`concurrency:` comments; `ci-doc-only.sh --select`):

- **A verdict under cancel churn.** It sits in a concurrency group of its
  own, so no push replaces it. Push gates still cancel each other: 222 of 673
  this week (33 %). The gaps between two finished push gates (n=451): max
  392 min, 14 gaps over 60 min, 1 over 180 min. In those gaps the hourly run
  was master's only verdict.
- **The per-part base.** Classify takes each part's base from the newest
  finished push **or schedule** runs where all that part's jobs were green. A
  green full hourly run resets every part's base at once. Fewer hourly runs
  mean older bases, a longer range per push, and so more carried code in the
  push gates (1.4: 57 of 145 docs-only gates already ran code they carried).

### 1.8 Re-measure of the first numbers (holder's answer 1528af5d)

Those were the newest 1,000 runs (23.11 18:05Z..24.11 12:44Z): 431
push-started, 7.2 workflows per commit, 372 started by another run, 368
skipped, 191 on a timer. The 7-day window agrees: 7.19 push-started runs per
push (4,839 / 673), 38 % workflow_run (4,111) and 38 % skipped (4,024, all
wf 12), 16 % timers (1,710). One correction: it is **7.2 per push**, not per
commit; a push carried 1.7 commits on average (1,142 / 673).

## 2. Findings

1. **The money question is moot today**: a public repo, USD 0 net. The real
   costs are verdict time, the shared job pool, API calls and noise.
2. **One workflow is the volume**: wf 10 is 80 % of the minutes. Inside it,
   **two parts** are ~80 % of a push run's minutes: the WUI e2e (8 shards,
   131 min) and the orc hermetic suite (4 shards, 58 min).
3. **The hourly full gate is the single largest line: 32 % of all minutes**
   (241 min x 168). In this week it added no persisting catch over the push
   gates (1.7), but it is also master's verdict when push gates cancel each
   other and the base the per-part selection starts from (1.7.1).
4. **"Bypass CI for a small docs change" already exists** (the express docs
   lane, per-part selection). It fired on 88 of 145 docs-only gates; the rest
   paid for code that earlier pushes carried. What a docs push still runs is
   hygiene, which is exactly the job that catches a 2026-09-21-style defect
   (C2: a banned name in a `spec.md` cost 12 red runs). A bypass that drops
   hygiene would have let C2 through.
5. **The run count is inflated, not the minutes**: 38 % of all runs are
   wf 12 skips (0 minutes, at most 6 reruns in 4,110), and 4 small workflows
   start on every push with no path filter (15, 25, 26, 64; 10 is the fifth)
   at ~1..2 billed minutes each, mostly rounding (0.4..0.5 real minutes in a
   1-minute bill). 32 (docs publish, path-filtered) adds ~3 on a docs push.
6. **Duplicate work**: a hub push tests the hub twice (wf 10 and wf 20); an
   orc-only push runs the hub part (24 min) by the part map's rule, and at
   the dir level the hub suite reads, every one of the 107 needed it (A4).
7. **Two timers find nothing most of the time**: wf 40 reconciled in 0 of 40
   sampled runs; wf 21 reached its dispatch step in 8 of 40.

## 3. Candidate actions

Minutes are billed minutes per 7 days, from section 1. "Risk" names the
2026-09-21 defect (C1 domain literal, C2 banned name in a doc, C3 i18n key,
C4 tfvars/image drift, C5 e2e layout, C6/C7/C9 hub flakes) or a red since
that the action could have let through. Nothing here is decided.

| # | action | saves (min / 7 d) | risk | the test that proves it |
|---|---|---:|---|---|
| A1 | Hourly full gate every **3 h** instead of every hour (`43 */3 * * *`) | **upper bound** ~27,000 (2/3 of 40,488), 21 % of all; part comes back as push minutes (older part bases, more carried code), not measured | (1) a part-map miss or a flake surfaces up to 3 h late instead of 1 h; this week 0 persisting only-hourly reds (1.7, n=168); (2) under cancel churn (222 of 673 push gates cancelled) master can go up to 3 h with no verdict at all (1.7.1: one push-verdict gap of 392 min this week); (3) part bases age, so push gates carry more code (1.7.1) | `gate10-concurrency.tst.sh` case: the cron reads `*/3`; schedule runs a day = 8; and over a set window (n stated) before and after, the share of push gates that run carried code, the push-gate minutes, and the longest gap between two master verdicts |
| A1b | Skip the hourly run when its head already had a finished **all-parts** gate | 3,374 for the 14 "same head as the last hourly" runs; more if an all-parts push gate counts too (not measured) | none of the six; every new head still gets a full run; all 14 same-head runs followed a green run (1.7), so no red re-check is lost this week | a planted head with a green full gate starts no code jobs; a new head runs all; a head whose last full gate was red still runs |
