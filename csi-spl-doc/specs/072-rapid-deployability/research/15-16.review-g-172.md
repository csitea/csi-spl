## 2. Blockers

1. **Nothing to download.** T2, T4. Every install and every upgrade is a compile. `install.sh:6`, `docker-compose.yml:49`.
2. **The image we already push cannot be the client's image.** Section 1.3. A release that publishes the Cloud Run image and points compose at it fails in `hub-init` (no `psql`, no `init`).
3. **Compose needs the tree.** `docker-compose.yml:36` bind-mounts `pg-init.sh`. A three-file bundle cannot boot until that mount is gone.
4. **One web image cannot serve two domains.** `SPOOL_PUBLIC_URL` is a build arg (`docker-compose.yml:142`). Off localhost the client rebuilds.
5. **The agent installer is a moving build.** Newest Go from `go.dev` (`install.sh:276`) against `go 1.25.14` (`go.mod:5`); newest yq (`install.sh:241`); `grep -c releases/download` -> 0. `--update` follows trunk (`install.sh:113`) while the upgrade text says pin a stable (`README.md:115`).
6. **The only published note lists a migration the release does not contain** (T9), and its "52" is not the schema (T10, 77 files). `release-stable.func.sh:145`.
7. **No upgrade has been run.** Wf 50 is a fresh master stack (`50_oss-standalone.yml:12-22`). The real gap is 77 files to 112 (T10). `Migrate` will not notice a renamed applied file (`migrate.go:69-76`). Rollback is the README dump (`README.md:105-109`).
8. **The version a zip build prints is the floor `1.1.3-dev`** (T7), while the release title says `v2.2.0` and trunk's counter is `v8.4.0` (T6). Three names, none of them "what you are running" for a client who did not pass `SPOOL_VERSION`.
9. **The odometer ends at 9.9.9, 159 deploys from here** (T6). After that `do_release_version` cannot mint, so the `(vX.Y.Z)` on the next stable title stops too. `stable-<date>` does not use that counter. The code change is already research 05's; it is listed here because a release review that skips it will document a number that is about to die.
10. **No CLI/hub contract** (section 1.2, zero matches). A box built from any commit talks to any hub until a request fails with a protocol error.

`SECURITY.md:28-33` still says rebuild from `master` for a security fix, and that the next weekly stable carries it. The weekly cut has one tag and has not yet had a Monday (T3).

## 5. Where I disagree

Measured against `research/15-client-path.md` (tree `e3b1627e` in its header) and `research/16-release-artifacts.md` (`d0fbbcf7a` in its header, commit `ee04fd2d` on this fetch). Same repo, 2026-10-04. Their counts that I re-ran and still match are not listed: 0 assets, no `ghcr` in workflows, `install.sh` builds from source, WUI build-arg, wf 50 on master only.

1. **Public `v*` image tags (15 C1, 16 R1 and Q2).** Both put `v<X.Y.Z>` on the image a client is offered, and 16 Q2 recommends images on every build. I disagree (Q1, T6). `stable-<date>` is the only public tag. Our private registry already keeps every build.
2. **Which Dockerfile is "the" hub image (neither note).** 15 C1 and 16 R1 say push `spool-hub` as if wf 20's image were the client artifact. It is not (section 1.3, blocker 2). The distroless image's entrypoint is the `spool` binary; compose `init` is a shell script that needs `psql`.
3. **Upgrade window (16 Q3 vs 15 Q5).** 16 recommends testing the last four stables. One stable exists, and it is 35 migration files behind trunk (77 vs 112). I take 15's "any later stable", with 16's test shape, but the first fixture has to be this gap (X6), not a one-step synthetic range.
4. **README quick start switches to the stable tag now (16 R5).** I disagree until X1 and X6 are green. `git rev-list --count stable-2026-09-29..origin/master` -> 1291 at `80874f74`. The quick start is the path wf 50 proves. The upgrade section already tells an existing install to pin a tag (`README.md:115`).
5. **A version warning is enough (15 C9).** I disagree. 16 R9 (refuse, print the upgrade command) is the error a person can act on. 15 Q3 is right that a release-API call stays off unless opted in (X7).
6. **Cosign on the client's first command (15 C6).** I disagree that it is part of install. `sha256sum -c SHA256SUMS` uses a tool the machine already has (X2). Signing can follow; it does not shorten the first deploy.
7. **The false migration (15 missed it, 16 R2 is right).** Re-measured here: the published body names `0040_tenants_display_name.sql` once and the tag has zero such files (T9). 16's cause (`release-stable.func.sh:145`, added-in-history rather than present-at-tip) matches the code I read. Extra, not in 16's table: the same body says 52 migrations while the tag contains 77 files (T10). X5 counts the tree on a first cut.
8. **Leaving the 9.9.9 cliff out of a release review (16's opening).** The function edit belongs to research 05, and this file does not ask anyone else to make it. Omitting the cliff from section 16 still hides that the `v2.2.0` in the release title is the same counter that has 159 steps left (T6). Client docs should not teach that number as the version to pin.
