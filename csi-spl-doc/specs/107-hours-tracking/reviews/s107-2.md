# 107 Hours tracking: panel review, seat s107-2

**Seat**: s107-2 (agy, a-530) · **Reviewed**: `csi-spl-doc/specs/107-hours-tracking/spec.md` at `dae04f97` (seat s107-1 draft)  
**Date**: 2026-10-07 · **Topic**: t1 `ef217164-daaa-43bb-8343-f55ddb2f53a8` · lane dispatch `dispatch-ef217164`  
**Tree measured**: origin/master at `dae04f97`

**Verdict: agree with the shape, change eight things before the build.**

The draft is strong on the fundamentals: computing suggestions on read without batch worker jobs, keeping raw activity signals strictly private to the member, using a watermark freeze mechanism, and providing a clean two-step approval flow (worker approves rows, biz owner approves frozen member periods).

Judged against the owner's three core requirements in order:
1. **LIGHTWEIGHT**:
   The draft reuses existing tables (`messages`, `calendar_events`, `tenants.settings`, RBAC), but departs from lightweight principles by declaring unindexed database reads for message edits/reactions and adding an unused surrogate UUID primary key to `hours_entries`. It also omits the required database constraint update for the left rail.
2. **VERY USER-FRIENDLY**:
   The desktop flow (2 clicks: open Hours -> Approve week) and mobile flow (2 taps: rail -> Approve day or sticky Approve week) fulfill the requirement without forms. However, the return path is incomplete: when a biz owner returns a member's hours with a note, no in-app alert or notification reaches the worker, leaving them in the dark unless they happen to visit `/hours`.
3. **SUGGESTIONS**:
   Active-tab minutes solve the chat hub's reading blindness. However, the definition of time worked in Section 1 has two critical flaws: the 3-minute floor naively discards short, focused message posts, and calendar event suggestions inadvertently count deploy freezes and reminders as worked time.

## 1. Facts checked against the code and schema

### 1.1 Signals and query indexing on trunk
- **Posts and replies**: `messages_from` index `(tenant_id, from_box, from_id, ts)` (rdb `0001_hub_core.sql:82`) exists and is durable. A range scan for a member's posts in a day is indexed and fast.
- **Message revisions**: `message_revisions` (rdb `0026_message_revisions.sql:52`) has `PRIMARY KEY (tenant_id, msg_id, revision)`. There is **no index** on `(tenant_id, edited_by, edited_at)`.
- **Message reactions**: `message_reactions` (rdb `0037_message_reactions.sql:23`) has `PRIMARY KEY (tenant_id, msg_id, actor, emoji)`. There is **no index** on `(tenant_id, actor, created_at)`.
- **Table scans prohibited**: Spec §2 line 109 claims "one indexed read each for posts, minutes, and events". Querying edits or reactions directly would require full table scans across all message revisions and reactions in the tenant, violating performance rules (spec 027). Furthermore, any in-app editing or reacting already generates active-tab minutes in the WUI. Edits and reactions must not be queried as separate signals in the suggestion engine.
- **Presence and reading cursors**: `humanOnline` (`internal/hub/channels.go:399`) is an in-memory socket count on `s.online`, never written to disk. `read_marks` (rdb `0098_read_marks.sql:23`) has `PRIMARY KEY (tenant_id, member_id, mark_key)` and overwrites the watermark on every sync (`internal/store/read_marks.go:168`), destroying history. Thus, the active-tab minute is the only viable way to measure reading.

### 1.2 Calendar event kinds
- `calendar_events.kind` (rdb `0125_calendar.sql:24`) has constraint:
  `CHECK (kind IN ('release', 'deploy', 'maintenance', 'freeze', 'agent_task', 'reminder', 'other'))`.
- A deploy freeze (`kind = 'freeze'`) or reminder (`kind = 'reminder'`) can be created by a human with timed start and end. Under §1.4 as written, an engineer who created a 2-hour deploy freeze window would have 2 hours suggested as worked time. The suggestion query must filter on `kind`.

### 1.3 Rail order constraint
- `humans.rail_order` has check constraint `humans_rail_order_check` (rdb `0133_human_rail_order_calendar.sql:10-26`), which strictly checks allowed arrays up to 11 items ending with `calendar`.
- Adding `hours` to the left rail without updating this database constraint causes saving a member's rail order preferences to fail with a CHECK constraint error. The migration must widen `humans_rail_order_check` to 12 items including `'hours'`.

### 1.4 Primary key on `hours_entries`
- Spec §3.2 specifies `entry_id uuid PK with tenant` alongside `UNIQUE (tenant_id, member_id, day, target)`.
- `entry_id` is never referenced anywhere: signoffs are per-member per-period (`hours_signoffs`), reports group by member/day/target, and the WUI submits batch PUT updates. Maintaining both a UUID PK and a UNIQUE constraint wastes 16 bytes per row and doubles index maintenance overhead. The natural primary key is `(tenant_id, member_id, day, target)`.

## 2. Answers to the reviewer questions (Spec Section 12)

### Q1: Is the active-tab minute (1.2) the right single new signal, and "input in the last 60 s" the right test?
**Yes.**
- Without active-tab minutes, reading in topics/issues counts as 0, which would drastically under-report time worked in a collaboration tool where reading outweighs writing.
- "Input in the last 60 s" combined with Page Visibility (`document.visibilityState === 'visible'`) prevents background tabs or overnight idle windows from logging phantom hours.
- Bridging with idle cutoff N = 10 minutes ensures that pauses while reading a long document or thinking about a response are bridged smoothly.

### Q2: N = 10 and the 3-minute floor: right defaults?
**N = 10 is the right default; the 3-minute floor needs qualification.**
- N = 10 is well-balanced: long enough to bridge typical pauses in discussion or document review, but short enough to avoid rolling breaks into worked blocks. Making it workspace-configurable (range 5..30) gives tenants flexibility.
- The 3-minute floor is correct for *passive reading* (opening a tab for 60 seconds without interaction should be dropped). However, it must **never drop a block containing a message post or reply**. If a user logs in, sends a quick reply to an urgent inquiry (taking 1-2 minutes), and closes the tab, that is tangible work and must not be zeroed out.

### Q3: Is "return reopens that member only" (4.3) simpler than a workspace unfreeze, and does it keep the freeze meaningful?
**Yes, decisively so.**
- Workspace-wide unfreeze introduces significant business risk: unlocking all members' approved timecards when only one person had an error risks unintended modifications and disrupts accounting/billing records.
- Reopening only that member's period isolates the correction, preserves the frozen and signed-off status of all other team members, and records an auditable trail (`hours.return` with required explanation note).

### Q4: Is a rail item + one page the smallest UI, or can Hours live inside an existing page without touching 089/106?
**A rail item + one page is the smallest and cleanest UI.**
- Putting hours inside Calendar would violate the instruction not to touch 089/106 files and would bloat the calendar mobile bundle.
- Putting hours inside Settings hides a routine weekly member task inside an administrative area.
- A dedicated rail item `/hours` loading lazily (spec 027) keeps mobile and desktop layouts isolated, modular, and performant.

### Q5: Three tables: can any be dropped (e.g. signoffs into `tenants.settings`, or entries carrying the signoff)?
**No, the three table boundaries are necessary, but `hours_entries` should drop its surrogate UUID.**
- Folding signoffs into `tenants.settings` JSONB would cause severe write contention and row-level locking on the `tenants` table on every biz owner approval or return, and would create unbounded JSON bloat over time.
- Carrying signoffs on `hours_entries` rows would force multi-row updates across 20-30 rows per member period, would fail to represent 0-hour periods (e.g. holiday/leave weeks with no entries), and would duplicate return notes across many rows.
- Dropping `entry_id uuid` from `hours_entries` and using `(tenant_id, member_id, day, target)` as the natural primary key achieves lightweight data storage without altering table boundaries.

## 3. Numbered changes

### S2-1: Section 1.2 & Section 2 — Drop unindexed message edits and reactions from suggestion query
- **Section**: §1.2 line 59, §2 line 109.
- **Problem**: `message_revisions` (rdb 0026) and `message_reactions` (rdb 0037) have no index on member/actor or timestamp. Querying them on read would trigger tenant-wide table scans. Furthermore, in-app edits and reactions already produce active-tab minutes.
- **Fix**: Drop message edits and reactions from the SQL query signals in §1.2 and §2. Clarify that edits and reactions are covered by the active-tab minute signal in the WUI. The suggestion computation on read consists strictly of three indexed reads:
  1. Message posts: `messages_from` index `(tenant_id, from_box, from_id, ts)`.
  2. Active-tab minutes: `hours_minutes` PK `(tenant_id, member_id, minute)`.
  3. Meetings: `calendar_events` index `(tenant_id, starts_at, ends_at)` + `calendar_guests` PK `(tenant_id, event_id, guest_id)`.

### S2-2: Section 1.1 — Refine the 3-minute floor rule for active posts
- **Section**: §1.1 item 4.
- **Problem**: Rule 4 drops any block under 3 minutes ("a glance at the phone is not work"). If a member writes and sends a message or reply in 1-2 minutes, their work is dropped to 0:00.
- **Fix**: Split the rule:
  - Blocks consisting solely of passive active-tab minutes (no posts) under 3 minutes are dropped.
  - Blocks containing at least one counted message post/reply are retained with a 3-minute minimum credit.

### S2-3: Section 1.4 & Section 7 — Filter calendar event kinds
- **Section**: §1.4 line 86.
- **Problem**: `calendar_events.kind` includes `'release', 'deploy', 'maintenance', 'freeze', 'agent_task', 'reminder', 'other'`. Timed confirmed events created by a member would suggest deploy freezes, system maintenance, and reminders as worked hours.
- **Fix**: Exclude non-meeting kinds:
  `WHERE kind NOT IN ('freeze', 'reminder', 'deploy', 'maintenance')` (or restrict suggestions to events where `kind = 'other'` or events with multiple human participants).

### S2-4: Section 3.2 — Make `(tenant_id, member_id, day, target)` the natural PK of `hours_entries`
- **Section**: §3.2 `hours_entries`.
- **Problem**: Having both `entry_id uuid PK` and `UNIQUE (tenant_id, member_id, day, target)` creates an unnecessary surrogate key and two separate btree indexes. `entry_id` is never referenced by signoffs, routes, or exports.
- **Fix**: Drop `entry_id uuid`. Define `PRIMARY KEY (tenant_id, member_id, day, target)`. Upserts use `INSERT INTO hours_entries (...) VALUES (...) ON CONFLICT (tenant_id, member_id, day, target) DO UPDATE SET ...`.

### S2-5: Section 3.2 & Section 5.1 — Add rail order constraint migration
- **Section**: §3.2 and §5.1.
- **Problem**: `humans.rail_order` has a database CHECK constraint `humans_rail_order_check` (rdb 0133) strictly validating up to 11 rail items ending in `'calendar'`. Adding `'hours'` breaks saving rail order preferences.
- **Fix**: In the migration (`0150_hours_tracking.sql`), include `ALTER TABLE humans DROP CONSTRAINT humans_rail_order_check;` and re-add the constraint allowing a 12th item `'hours'`.

### S2-6: Section 3.2 — CHECK constraints on `hours_minutes` and `hours_entries`
- **Section**: §3.2.
- **Problem**: `hours_minutes.minute` must be truncated to the minute to prevent sub-minute collisions. Allowed target patterns should be strictly enforced at the database level.
- **Fix**:
  - On `hours_minutes`: add `CHECK (minute = date_trunc('minute', minute))` and `CHECK (target ~ '^(t|ch|dm):.{1,200}$|^ws$')`.
  - On `hours_entries`: add `CHECK (target ~ '^(t|ch|dm|cal):.{1,200}$|^ws$')`.

### S2-7: Section 4.3 — Return notification for workers
- **Section**: §4.3.
- **Problem**: When a biz owner returns a member's period with a required note, the member receives no notice and has no way of knowing their hours were rejected without visiting `/hours`.
- **Fix**: Specify that returning a member's period triggers an immediate in-app pop-up / notification to that member ("Your hours for <period> were returned: <note>"), with a direct link to `/hours?period=<period>` to review, correct, and resubmit.

### S2-8: Section 6.2 — XLSX export HTTP contract and structure
- **Section**: §6.2.
- **Problem**: §6.2 mentions generating XLSX with Go's `archive/zip` and `encoding/xml` with two sheets, but lacks HTTP response headers and cell typing specifications.
- **Fix**: Specify:
  - Headers: `Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `Content-Disposition: attachment; filename="hours-<tenant>-<from>-<to>.xlsx"`.
  - Implementation: Placed in `internal/xlsx` helper package; generates minimal valid OpenXML parts (`[Content_Types].xml`, `_rels/.rels`, `xl/workbook.xml`, `xl/worksheets/sheet1.xml`, `xl/worksheets/sheet2.xml`).
  - Cell typing: Numeric cells (minutes and decimal hours) must use `type="n"` with standard number formats so spreadsheet software can compute sums and averages natively.
