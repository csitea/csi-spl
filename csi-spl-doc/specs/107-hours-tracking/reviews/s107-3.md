## 2. Changes

### S3-1. Section 1.2 / 2 / 3.2: post signals expire before a `month` period freezes. Write post minutes into `hours_minutes`

- **Problem.** Suggestions read posts, edits and reactions from `messages` at read time. Messages expire after 720 h (section 1). The spec allows `period = month` with `freeze_grace_days = 2`, so day 1 of a 31-day month is 33 days old when it freezes. Its posts are already gone, so its suggestion drops while the worker is still approving it. Any operator who shortens `SPOOL_HUB_RETENTION_CHANNELS` breaks `week` too. Reading `messages`, `message_reactions` and `hours_minutes` and merging them in Go is also three read paths where one would do.
- **Fix.** The hub writes the post minute itself. When a member posts, edits or reacts from `box-wui`, the hub upserts `hours_minutes (tenant, member, minute, target = t:<task_id>, src = 'post')` in the same transaction: one indexed upsert per post. A post overrides a tab row for that minute (`ON CONFLICT ... DO UPDATE ... WHERE hours_minutes.src = 'tab'`), so the 1.3 rule "the post wins" is enforced at write time, not computed later. Suggestions then read **one table plus the calendar**, retention no longer affects hours, and Q1-B (no tab tracking) still works because the hub writes post rows anyway. Add `src text CHECK (src IN ('post','tab'))`. Posts carry no browser time zone, so `tz` = the member's last tz from a tab batch, else the workspace `tz`.
- **Effect on R1.** No new table and no new route. `messages_from` drops out of the read path.

### S3-2. Section 2 / 4.2 / 4.3: no suggestions on or before the freeze, also for a returned period

- **Problem.** Suggestions are computed on read. Raw minutes are pruned at the freeze, but calendar events are not. Under v0.1 posts survive too. So a **returned** period (4.3) shows meeting and post suggestions again, although 4.2 says unapproved suggestions "disappear" at the freeze. The worker then sees new rows in a period they believe was finished.
- **Fix.** One rule in section 2: **no suggestion is computed for a day `<=` the effective freeze, including a returned period.** In a returned period the worker edits, rejects and adds entries only. If owner Q2 = B (auto-approve), the freeze sweep writes those entries **before** it prunes `hours_minutes`. Write that order down.

### S3-3. Section 4.1 / 5.2: "Approve week" must not approve today. Accepting a delta takes one tap

- **Problem.** On Friday at 10:00, Approve week approves Friday's partial row. Friday afternoon's work then shows only as a "+3:10 since you approved" delta (section 2). At the freeze, unapproved suggestions count zero, so the delta is lost. The friendliest button (R2) silently undercounts the most common day.
- **Fix.**
  1. **Approve week / Approve day** approve **closed days** only (before the member's today). Today's card shows **Approve so far**, a separate tap.
  2. A delta row has its own **✓ +3:10**, one tap.
  3. **Approve week** stays enabled while any closed day in the period has open suggestions **or deltas**, and shows the count ("Approve week · 2 open").
  4. The freeze warning (S3-6) counts deltas as open.

### S3-4. Section 1.1 / 1.3 / 1.4: one precedence order, and no double counting of overlapping meetings

- **Problem.** 1.3 says "the post wins". 1.4 says "active minutes inside the event's span go to the meeting". So when someone takes notes in a topic during a meeting, the two rules disagree. Two overlapping `yes` events would each suggest their full length. Also, the 1.1 definition says meetings "attended", which the hub cannot see. It only sees an accepted invitation.
- **Fix.** Add to 1.3: **meeting > post > tab** for each minute. Meeting minutes are the **union** of the events' spans, and each minute goes to the event that started earliest. In 1.1, change "attended" to "**accepted (or created)**; a suggestion, like the rest".

### S3-5. Section 1.2: specify the active-tab minute properly (answers reviewer Q1)

- **Q1 answer: yes.** It is the right single new signal, and it is the only way reading counts. "Input in the last 60 s" is the right test, with two additions:
  - The test is `document.visibilityState === 'visible' && document.hasFocus()` **and** an input event (key, pointer, touch, wheel, scroll) in the last 60 s. A tab that is visible on a second monitor but not focused records nothing.
  - **Flush** from its own small in-memory buffer every 5 min, on `visibilitychange` to hidden, and on `pagehide` with `fetch(..., {keepalive: true})`. Read-sync pushes every 5 s (section 1), so "the moments read-sync already pushes" is wrong and should go. Lost on a crash: at most 5 min, which is acceptable for a suggestion.
- The batch carries `tz` once, not per row. The hub stamps it on each row it writes.

### S3-6. Section 4.2 / 3.1: no pop-up in v1. Use a count badge on the Hours rail item

- **Problem.** The "existing pop-up path" is `CalendarReminderPopup.vue` plus `plugins/calendar-reminders.client.ts`, which is 089 code that this spec must not touch. A new always-on client plugin also counts against the 155 KB initial chunk (027).
- **Fix.** v1 shows a **count badge** on the Hours rail item: closed days in the open period that still have suggestions or deltas. The Hours page shows a banner, "2 days not approved · freezes Wed 00:00". The badge count comes from the `GET /v1/me/hours` the page already uses, read lazily once per session and on focus. Put "pop-up / e-mail reminder" under **Not in v1**.

### S3-7. Section 5.1: keep the rail item, and list its real cost (answers reviewer Q4)

- **Q4 answer: the rail item is the smallest UI that meets R2.** Inside Settings it is 3+ taps on the phone. Inside the calendar it touches 089/106. A tab on Issues does not fit, because hours span channels and DMs.
- **Fix.** It is not free reuse. tasks.md needs:
  1. Widen `humans_rail_order_check` to a 12-item branch, in the same migration as the tables, forward-only, the 0133 pattern.
  2. Update `parseRailOrder` (`utils/rail-order.mjs:109`) so stored 11-item orders get Hours appended.
  3. Change the 5.1 line "placed by the existing rail order (rdb 0133)" to say "a 12th rail entry; widens the 0133 CHECK".

### S3-8. Section 3.1: the audit kinds need a CHECK widening

`member_activity.kind` is an enumerated CHECK (0091; 0148 widened it to add `password_reset`). Add the widening in the same migration: `hours.return`, plus `hours.unfreeze` only if Q4 stays A (see S3-10). Section 3.1 should call it "reused, with a CHECK widening", not plain reuse.

### S3-9. Section 6.2 / 5.4: cut the extras from v1 (R1)

These are not needed for "the biz owner approves and downloads CSV/XLS" (R7). Move them to **Not in v1**:
- The XLSX **second sheet** (totals per member) and the **total row**. v1 XLSX is the CSV's columns in one sheet. That is still a small `archive/zip` + `encoding/xml` writer, with no new dependency.
- **Round to 15 min** export option. The spreadsheet can do it.
- Team-tab **epic** filter and grouping, because it walks issue parents. Keep the filters for member, target type and issue.
- Arbitrary **from..to** range. v1 offers periods only, so every report lines up with a freeze and signoffs.

### S3-10. Section 4.2 / 4.4: a freeze that a late sweep cannot leak, and no workspace unfreeze (owner Q4 -> B)

- **Problem.**
  1. The freeze happens only when the sweep moves `frozen_through`. If the sweep is late or fails, writes to a period that should be frozen still go through.
  2. A workspace-wide unfreeze voids every signoff of the period. That is a second reopen mechanism with its own route branch, audit kind and voiding logic, and **Return** already covers the real cases. **Return all** handles a mass correction.
- **Fix.**
  1. The write path checks the **effective freeze** = max(`frozen_through`, the last period end whose `end + grace <= now` in the workspace tz, using the current `period` for days after `frozen_through`). The sweep only **persists** that value and prunes. The freeze is then exact whether or not the sweep has run. **Freeze now** only moves the watermark forward.
  2. Recommend owner **Q4 = B**: no workspace unfreeze. Add **Return all** to the Team header (one note, every member of the period). That drops `hours.unfreeze`, the unfreeze half of `POST /v1/hours/freeze` (which becomes **Freeze now** only) and the signoff voiding.
- **Q3 answer: yes.** "Return reopens that member only" is simpler than an unfreeze, and it keeps the freeze meaningful. Only the biz owner can do it, it is per member, it carries a note and an audit row, and it ends in a new freeze plus signoff.

### S3-11. Section 1.1: the 3-minute floor drops tab-only blocks only (answers reviewer Q2)

- **Q2 answer:** N = 10 is right. It bridges reading between posts without padding a long break, and the 5..30 range is enough.
- **Fix.** The 3-minute floor applies only to blocks that contain **no post**. Otherwise, a day of five isolated phone replies, each a 1-minute block, is suggested as 0:00. Those replies are work the hub can prove. A glance at the phone (tab-only, under 3 min) is still dropped.

### S3-12. Section 1.7: state the privacy line exactly

"Nobody else reads them: ... not an operator view in the WUI" is right. The table, however, has `operator_scope`, which the prune sweep needs. Write it as: **no route returns another member's raw minutes or unapproved suggestions; `operator_scope` exists for the sweep's prune only, and no operator route reads `hours_minutes`.** The cross-tenant test (FR-10) should also assert that `GET /v1/hours` from a `hours.read` holder never returns `hours_minutes` rows or unapproved suggestions.
