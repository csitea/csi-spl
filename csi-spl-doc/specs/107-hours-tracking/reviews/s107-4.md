## 1. Changes

### S4-1 (section 1.2, 2): suggestions computed from `messages` lose a month period's first days

**Problem.** Section 2.1 computes suggestions on read from `messages`. But a message row is deleted when it expires. `0001_hub_core.sql:77` gives `messages.expires_at timestamptz NOT NULL`, and the expiry is `ts + retention(channel)`. `internal/hub/server.go:589-594` sets that to `RetentionChannels`, and `internal/config/config.go:304` defaults it to `envDefault:"720h"` (30 days; `alerts` gets 168h). With `period = month` and `freeze_grace_days = 2`, the first day of a 31-day month is 33 days old at the freeze. So its posts are already gone before the worker sees the period's last suggestions, and the "why" sheet for that day is empty. An operator who shortens retention breaks the feature for every period length.

A smaller point: the citation is wrong. `retention.go`'s `CommittedRetention` is the **deliveries** window (spec 059 S4), not the messages window. Only the number happens to match.

**Fix.** Make the new table the single source of truth for activity minutes: **one signal table, two writers.**
- The hub writes the `hours_minutes` row for a post, edit or reaction **when it stores it**. This is one upsert on the existing write path; the target is `t:<task_id>`.
- The WUI writes the active-tab minutes, as now.
- Suggestions then read **one** table (plus calendar events), whatever the message retention is. The pruning rule in 1.7 (prune at freeze or after 45 days) becomes the only retention that matters.
- Hub-written minutes have no browser time zone. They take the member's last `tz` sent by the WUI, and the workspace `tz` until the WUI has sent one.
- The precedence "the post wins" (1.3) becomes an upsert rule: a hub write overwrites a tab-minute's target, and a tab write never overwrites a hub write. That needs one `source` column (`post` | `tab`).

This also removes the `messages_from` read from the suggestion path (2.1 "one indexed read each" becomes one read).

### S4-2 (section 3.2, 4.2): the freeze watermark cannot live in `tenants.settings`

**Problem.** `tenants.settings` is the spec 098 registry: `internal/store/tenant_kv.go:18-31` says "the hub owns every key", each key is a flat dotted scalar (`"area.name"`, kind bool|int|string), and every write goes through the generic tenant settings route as `settings || $set - $unset`. Two things go wrong:
- **`frozen_through` as a settings key**: any holder of `tenant.settings` can set it through the generic route. That is a silent, unaudited unfreeze that bypasses 4.4. And a hub sweep writing a key that admins can also write is the race the registry was designed to avoid.
- **A nested `hours` object**: the registry has no object kind. The draft's `tenants.settings.hours.{period,...}` does not exist as written.

**Fix.**
- Settings become four registered scalar keys: `hours.period` (string: `week`|`two_weeks`|`month`), `hours.freeze_grace_days` (int 0..7), `hours.idle_minutes` (int 5..30), `hours.tz` (string). That is four `RegisterTenantSetting` calls and no DDL, which is exactly 098's "adding a setting is a RegisterTenantSetting call".
- **Drop `frozen_through`.** Store the freeze in the table that already exists for periods; see S4-3.

### S4-3 (section 3.2, 4.2-4.4): one per-member period row carries freeze, return and signoff

**Problem.** The draft holds period state in three places: the watermark (frozen), a `returned` signoff that overrides the watermark for one member, and an `approved` signoff. So "is this day frozen for this member?" needs all three. Also, changing `hours.period` must not move the bounds of a frozen period, and a single date watermark cannot remember where past periods began and ended.

**Fix.** Rename `hours_signoffs` to **`hours_periods`**, one row per (member, period). The freeze sweep **creates** the row, so the stored `period_start/period_end` are the bounds that were in force at that time:

| `state` | set by | worker can edit | biz owner can |
|---|---|---|---|
| (no row) | | yes (the period is open) | see approved rows |
| `frozen` | the sweep, at `period_end + grace` | no | approve, return |
| `returned` | the biz owner (note required) | yes, then Resubmit -> `frozen` | |
| `approved` | the biz owner | no (final) | |

- A day is editable when no row covers it, or when its row is `returned`. That is one indexed lookup.
- The sweep writes one row per member who has an entry or a suggestion in the period. A member with nothing gets no row and nothing to sign off.
- An unfreeze (if the owner wants one, Q4) deletes the period's rows and writes `member_activity`. Nothing else stores freeze state.
- Changing `hours.period` affects only periods that have no rows yet. This is exactly what 4.2 asks for, and it needs no extra rule.

Still three tables, but the third now earns its place twice. It also answers reviewer question 5 (section 2).

### S4-4 (section 3.1): `member_activity` needs a CHECK change

**Problem.** Table 3.1 says the audit rows `hours.return` and `hours.unfreeze` are "reused" with no DDL. But `member_activity.kind` is a closed CHECK list. It was set in `0091_member_activity.sql:20` and redefined in `0148_session_revocations.sql:29-30` (`DROP CONSTRAINT member_activity_kind_check` / `ADD CONSTRAINT ...`). An insert of `hours.return` fails today. The 0091 header also describes the table as events "ABOUT a member" with a 90-day sweep of auth rows. That fits a return (it is about the member), but the sweep's kind filter must not prune the hours rows.

**Fix.** The hours migration redefines `member_activity_kind_check` the way 0148 does: it adds `hours_returned` (and `hours_unfrozen` only if Q4 = A), using the table's underscore style rather than a dot. The spec says that the 90-day sweep keeps these rows.

### S4-5 (section 4.4, 6.3, 13 Q4): no workspace unfreeze and no "freeze now" in v1

**Problem.** Section 4.4 itself says unfreeze is "rarely needed now that a return reopens one member". It still costs a route (`POST /v1/hours/freeze`), a permission path, an audit kind, signoff voiding, and an owner question. "Freeze now" has no requirement behind it: R4 says weekly by default, configurable, which the sweep already covers.

**Fix.** Move both to "Not in v1" and drop the route (6 routes, not 7). Change Q4's recommendation to **B: none in v1, Return is the only way back**, and keep A as the option the owner can pick. Under S4-3, adding the unfreeze later is one route that deletes rows. Nothing has to be designed now to allow it.

### S4-6 (section 1.2, 1.7): say the raw-minute privacy rule precisely, and let the member turn tab minutes off

**Problem.** Section 1.7 says nobody else reads raw minutes, "not an operator view in the WUI". But `hours_minutes` is RLS **tenant** scoped (3.2). RLS separates workspaces, not members, and the `operator_scope` policy reads every row. So the guarantee comes from the routes, not from the database, and the spec should say that. Second, the active-tab minute is the one piece of new tracking in the spec, and Q1 asks the owner about it only for the workspace as a whole.

**Fix.**
- 1.7 says: "Only `/v1/me/hours*` serves raw minutes, always filtered `member_id = caller`. No other route reads `hours_minutes`, and a test asserts it (grep for the table name outside the hours store file). Operator database access is outside the WUI."
- Add one per-member toggle in the existing view prefs (**no new table**): "Count my reading time" (on by default if the owner picks Q1 = A). When it is off, the WUI sends no tab minutes, and that member's suggestions come from posts and meetings only. Q1 then decides the workspace default, and nobody is forced to be tracked.

### S4-7 (section 5.2, 9 acceptance): count the taps from where the member actually is

**Problem.** "Tap Hours in the rail -> Approve day: 2 taps" holds only when the rail is on screen. On the phone (043) a member reading a topic is at level 2 or 3, so it takes Back x1-2, then Hours, then Approve: up to 4 taps. The reminder pop-up (4.2) is already the moment the member is asked. Today it only informs.

**Fix.**
- The reminder pop-up carries **[Approve N days]**. One tap approves the open suggestions it names, and **[Review]** opens Hours at that period. The common case is then 1 tap from anywhere. It reuses the existing pop-up path, so there is no new screen.
- The acceptance test (9) adds: from inside a topic at 390 px, the week is approved in 2 taps or fewer via the pop-up.
- Keep the rail item. It stays the place to review and edit.

## 2. Answers to the reviewer questions (spec section 12)

1. **Is the active-tab minute the right single new signal, and "input in the last 60 s" the right test?** Yes. It is the only way to count reading. `read_marks` is overwritten on every sync (`PRIMARY KEY (tenant_id, member_id, mark_key)`, `0098_read_marks.sql`), and presence lives only in memory (`internal/hub/channels.go:399`). 60 s of input is the right test: reading a long post without scrolling for more than 60 s is still bridged by N. With S4-1 it is not the only *writer*: the hub writes post minutes into the same table. Add the per-member off switch (S4-6).
2. **N = 10 and the 3-minute floor?** Both are right. N = 10 bridges the read-think-type rhythm without counting a coffee break. A range of 5..30 per workspace is enough (Q3 = A). The 3-minute floor drops phone glances. Apply the floor **before** the "fold under 5 minutes into other" rule. The spec implies that order, but should state it, so a lane doesn't fold dropped minutes back in.
3. **Is "return reopens that member only" simpler than a workspace unfreeze, and does it keep the freeze meaningful?** Yes on both. Under S4-3 it is a single state change on one row. The freeze stays meaningful because only the biz owner can reopen, a note is required, and the action is audited. It is also why a workspace unfreeze can leave v1 (S4-5).
4. **Is a rail item and one page the smallest UI?** Yes. The calendar page is off limits (089/106), and an issue pane or topic header would cover only some targets. The two-tap common case comes mostly from the reminder pop-up (S4-7), not from the page. The page is still needed for review, edit and the Team tab.
5. **Three tables: can one be dropped?** No, but each needs a sharper job. `hours_minutes` is the only durable activity record (S4-1). `hours_entries` holds the worker's decisions per row. Folding them into periods would make the biz owner's per-member approval a per-row update. Signoffs **cannot** go into `tenants.settings`: that registry stores flat scalar keys that admins can write (S4-2). As `hours_periods` (S4-3), the third table replaces the watermark too, so the count stays at three and one mechanism disappears.
