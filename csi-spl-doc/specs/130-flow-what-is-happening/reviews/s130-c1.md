lines). Each agent's DMs are already its spool inbox, so a `dm` event for an
agent duplicates what `spool recv` delivers.

```sql
WITH l AS (SELECT tenant_id, msg_id, task_id, from_id, to_id, received_at FROM messages WHERE received_at > now()-interval '7 days'),
w AS (SELECT (SELECT count(DISTINCT p.from_id) FROM messages p WHERE p.tenant_id=l.tenant_id AND p.task_id=l.task_id
        AND p.received_at < l.received_at AND p.from_id !~ '^(HUM|GST)-' AND p.from_id <> l.from_id) aw,
      (CASE WHEN l.to_id IS NOT NULL AND l.to_id !~ '^(HUM|GST)-' AND l.to_id <> l.from_id THEN 1 ELSE 0 END) at FROM l)
SELECT count(*), sum(aw), sum(at), sum(greatest(aw, at)),
  percentile_cont(0.5) WITHIN GROUP (ORDER BY aw), percentile_cont(0.95) WITHIN GROUP (ORDER BY aw), max(aw) FROM w
```

It is a lower bound (posting only, no mention / `to` watches) and ignores
the channel door. New text:

> **What an agent gets**: `mention`, `blocked`, `ready` and `release`, the
> same rules as a human. NOT `dm` and NOT `reply`: its inbox already
> carries both. This keeps agent rows to mentions and blockers (prd 7 d:

> **The door**: agents are not in `channel_humans`, so the insert's door

## 6. Data and performance

CHANGE. Measured, not asserted:

**The write is not a connection problem.** The flow rows are CTEs of the
message INSERT statement (`flow_postgres.go:11-13,29`): one statement, one
connection, 0 extra round trips. "Batched asynchronously" would ADD a
second write path and a connection, the opposite of the goal. Private bench,
postgres:16-alpine, the 0104 table and both indexes, 8456 background rows
(prd's count), one INSERT ... SELECT from `flow_watches` per line, n = 200
lines per row:

| watchers per line | mean ms per line |
|---|---|
| 1 | 0.189 |
| 12 (agent p95) | 0.250 |
| 45 (agent max) | 0.504 |
| 665 (t1 members + 7 d agent ids, a release to "everyone" incl. agents) | 8.985 |

The page read for a member with 800 events is one `flow_events_member_at`
index scan, 30 rows, 0.109 ms, 32 buffers (`EXPLAIN (ANALYZE, BUFFERS)`,
same bench).

**So `release` must not fan out.** At ~86 versions a day, "everyone"
written as rows is 86 x 14 = 1204 rows a day for t1's humans and, with
agents, 86 x 665 = ~57 000 rows a day, each ~9 ms in the deploy's write.
Everyone gets the SAME release lines, so they are one read, not N rows. New
text:

> - **Fan-out**: per-member rows only for `mention`, `poke`, `dm`, `reply`,
>   `blocked` and `ready`, in `flowInsertCTE` (0 extra round trips, as
>   today). Measured prd fan-out 1.0303 (n = 8456 rows / 8207 lines);
>   with agents per section 5 it stays near 1 per line, because agents get
>   no `reply` / `dm` rows.
> - **Release**: no rows. The page read merges the newest `release_notes`
>   rows (ingested_at > the page's oldest event) folded per env per hour, and
>   the badge counts the folded release lines newer than `f:seen`. Needs an
>   index `release_notes (ingested_at DESC)` (0108 has only
>   `release_notes_version`).
> - **Badge**: unchanged for humans. Agents read counts with the page.
> - **Delete FR-008** ("batched to respect the 25-connection limit"): it
>   rests on a cost that does not exist.
