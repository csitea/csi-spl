## 2. The condensed view

CHANGE to c1's rule (c1 section 2), three corrections:

**(a) `blocked` folds too.** c1 says "`blocked` and `ready` never fold with
other kinds", which is right, but its line 1 then leaves `blocked` unfolded
per event. The owner seat alone received **550** blocker lines in 7 days (79
a day) over 313 (topic, hour) pairs: unfolded, they fill the 30-line first
page (`FLOW_PAGE`, `csi-spl-wui/src/utils/flow-entries.mjs:20`) more than
twice a day. New text for c1's point 1, last sentence:

> `blocked` and `ready` fold only with their own kind: one `blocked` line
> per topic per hour, with its count ("3 blockers in <topic>").

**(b) Fold the newest raw events, not the member's history.** c1 says "the
fold is done in the hub read (the page query groups)". A plain `GROUP BY`
over the member reads every event the member has. Bench (section 6): the
owner's 4665 events, n = 50 runs each:

| read | p50 ms | p95 ms |
|---|---|---|
| today's page, `ORDER BY at DESC LIMIT 30` | 0.281 | 0.357 |
| fold over the whole history, `GROUP BY task_id, kind, date_trunc('hour', at)` | **7.937** | 11.231 |
| fold over the newest 200 events (`ORDER BY at DESC, msg_id DESC LIMIT 200`, then group) | 1.006 | 1.323 |

The whole-history fold is a sequential scan of the member's rows and grows
with them; the bounded one stays an index scan. New text:

> The hub folds the member's newest 200 raw events (`FLOW_CAP`,
> `flow-entries.mjs:15`) into lines and returns the first 30. The cursor
> stays the raw `(at, msg_id)` of the oldest event the window read, so
> "Load more" folds the next 200; a (topic, kind, hour) group cut by the
> window edge shows as two lines, which is acceptable.

**(c) Opening a folded line marks all of it read.** A line folds N events;
if the open writes only `f:<newest msg_id>`, the other N-1 stay unread and
the line never clears. The covered check already accepts a topic mark at or
past the line (`flowCoveredSQL`, `internal/store/flow_postgres.go:82-89`,
the `'t:' || task_id` branch). New text:

> Opening a folded line writes the topic mark `t:<task_id>` at its newest
> event, which covers every older event of the group. A release line writes
> `f:rel:<version>` (the 0104 `mark_key` CHECK, line 69, admits it:
> `^(ch|t|dm|f):.{1,200}$`).

## 4. New kinds: release, ready, blocked

**`release`: DISAGREE with c1's read rule.** c1 proposes "merge the newest
`release_notes` rows (`ingested_at` > the page's oldest event)". That column
cannot say when a version went live:

- the ingest re-sends a 500-commit window every deploy
  (`RELEASE_NOTE_DEPTH` default 500,
  `csi-spl-orc/src/bash/run/release-note-ingest.func.sh`, header) and the
  upsert restamps every row it touches: `ingested_at = EXCLUDED.ingested_at`
  (`internal/store/release_note_postgres.go:115`);
- measured: `date_trunc('minute', ingested_at), count(*) FROM release_notes
  GROUP BY 1 ORDER BY 1 DESC` -> **500 rows at 17:12**, then 2, 3, 15. All
  5479 rows (1309 versions) carry an `ingested_at` inside the last 7 days.

So that rule would show ~500 commits as "just released" after every deploy.
The one moment the table does record is when a commit FIRST gets a version:
`version = coalesce(release_notes.version, EXCLUDED.version)` (same file,
line 110). New text for the `release` row:

> | `release` | A version first reaches this environment: the ingest gives
> a commit its version for the first time. Stored as a new column
> `release_notes.released_at`, set in the same upsert only when the stored
> `version` was NULL and the new one is not, never restamped. | Hub, at read
> time from `release_notes` (no rows), one line per version: prd had **83
> versions in 24 h, over 25 clock hours** (`count(distinct version),
> count(distinct date_trunc('hour', committed_at)) ... committed_at >
> now()-'24 hours'`), so they fold per hour: about 25 release lines a
> day. | `/releases/<sha>` of the version's newest commit |

Two facts the spec should state with it: each environment's hub has its own
`release_notes` (wf 20 runs the ingest per deploy job,
`.github/workflows/20_hub-build-deploy.yml:697-700`), so a prd Flow shows
prd releases only and no `env` column is needed; and the ingest is
`continue-on-error: true` (same file, line 699), so a failed ingest means
no release line, never a failed deploy.

**`ready`: AGREE with c1** (a structured `accepts` flag, no body parsing).
Re-checked: prd, 7 d, `count(*) filter (where body like 'ACCEPTED%')` -> **0**,
`like '%ACCEPTED%'` -> 640 (c1's 873 was an hour earlier on a sliding 7-day
window). One addition: `accepts` is a new optional key of the v:1 message,
so it goes into
`csi-spl-doc/specs/002-box-agent-messaging/contracts/message-schema.md` in
the same lane; an old box that drops unknown keys just emits no `ready`.

**`blocked`: AGREE, and it is mostly a relabel, not new rows.** prd, 7 d:
of 819 `blocker` lines, **593 already have a flow row** (619 rows), as a
`mention` / `dm` / `reply` (`count(distinct msg_id) filter (where exists
(SELECT 1 FROM flow_events f WHERE f.msg_id = m.msg_id))`). New text for
the row:

> `blocked` is the strongest rank in `flowInsertCTE` (ahead of `mention`):
> the same candidates as today's ranks get the row, its kind is `blocked`.
> No new candidate set; measured, it adds rows only for the 253 lines a
> week addressed to agents (section 5).

## 5. Agents: they get the same Flow

AGREE with c1: `spool_flow` does not exist (`grep -n '"spool_'
internal/mcp/mcp.go` -> 6 tools, none of them a flow), the kinds an agent
gets (no `dm` / `reply`: its inbox has them), no backfill.

**DISAGREE with c1's read door.** c1 proposes "a box-signed twin of `GET
/v1/view/flow`". No hub HTTP route takes a box signature today: the CLI
reaches the hub over its WebSocket session, and `spool issue` is the
worked example of an agent reading hub-held data that way: `hubclient.Issue`
dials `wire.RoleCLI` (`internal/hubclient/issue.go:24`) and sends a
`wire.TIssue` frame (line 35) that `onIssue` answers
(`internal/hub/issues_agent.go:29`). New text:

> **How they read it**: `spool flow [--kind] [--limit] [--before]` sends a
> `flow_read` frame on the CLI session, answered by the same `FlowRead` the
> WUI route calls, keyed by the session's agent (the `spool issue` path:
> `hubclient/issue.go`, `hub/issues_agent.go`). The MCP tool `spool_flow`
> wraps the CLI. Not `flow`: that frame type is the WUI's live push
> (`internal/hub/flow.go`, `flowFrame`).

**CHANGE: the agent's key is `<id>@<box>`.** `flow_events` is keyed
`(tenant_id, member_id, msg_id)` (0104 line 39). An agent id alone is not
one actor: prd t1, 7 d, **651** agent ids posted from **805** (id, box)
pairs, and **154** ids posted from 2 or more boxes (`count(distinct
from_id), count(distinct (from_id, from_box))`, `from_id !~
'^(HUM|GST)-'`). Keyed by the bare id, `c-001` on one box would read the
other box's blockers. New text:

> An agent's `member_id` is `<id>@<box>` (the same form the spool uses for a
> remote peer); `IsFlowMember` (`internal/store/flow_mentions.go:119-120`)
> and the insert's filter (`flow_postgres.go:39`) admit it for the agent
> kinds only.
