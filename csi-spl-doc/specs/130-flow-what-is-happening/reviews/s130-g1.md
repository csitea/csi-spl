## 5. Agents: they get the same Flow

CHANGE. Two facts.

**There is no read path.** MCP tools are `spool_put_file`, `spool_send`, `spool_recv`, `spool_get_file`, `spool_tail`, `spool_issue` (`grep -n "Name:" internal/mcp/mcp.go` -> 109, 113, 117, 121, 125, 129). No `spool_flow`. `git grep -n spool_flow origin/master -- '*.go'` hits only `spool_flow_place_key` in `flow_postgres.go:16,50`. The HTTP route refuses a non-human (`flow.go:109-115`). 062 already parked the tool outside itself (`062` spec section 5.3, "Later, outside 062"). The desk pane is the local inbox, not this table.

**"The same flow" is not a contained fan-out.** If every non-human who has already posted in the task got a reply row, prd 7 d would write **38655** agent rows on **13433** lines (p50 = 1 prior agent, p95 = 12, max = 32). Same hour, human `flow_events` were 5074. 38655 / 5074 = **7.6x**. Query:

```sql
WITH posts AS (
  SELECT tenant_id, task_id, from_id, min(received_at) AS first_at
  FROM messages
  WHERE received_at > now() - interval '7 days' AND from_id !~ '^(HUM|GST)-'
  GROUP BY 1, 2, 3
),
w AS (
  SELECT (SELECT count(*) FROM posts p
          WHERE p.tenant_id = l.tenant_id AND p.task_id = l.task_id
            AND p.first_at < l.received_at AND p.from_id <> l.from_id) AS aw
  FROM messages l
  WHERE l.received_at > now() - interval '7 days'
)
SELECT count(*), sum(aw), percentile_cont(0.5) WITHIN GROUP (ORDER BY aw),
       percentile_cont(0.95) WITHIN GROUP (ORDER BY aw), max(aw) FROM w
```

That count is posting only. It is a lower bound on "everyone who has posted watches", and it ignores mentions. Separately, 7684 of those lines are already `to` a non-human: the inbox has them. Giving the agent a `dm` or `reply` row duplicates `spool recv`.

Replace the two bullets with:

> - **How they read it.** A box-signed twin of `GET /v1/view/flow`, a CLI `spool flow [--kind] [--limit]`, and an MCP tool `spool_flow` over that CLI. All three are new, in L1. The desk pane is out of v1.
> - **What they get.** `mention`, `blocked`, `ready`, `release`. Not `dm` and not `reply`: the inbox already delivers both, and reply-watches would multiply the table by the 7.6x above. The insert's `^(HUM|GST)-` filter and `IsFlowMember` widen for those kinds only. The channel door (`flow_postgres.go:40-42`) needs the agent's channel membership as a second branch, or a public channel, or the mention is dropped.

## 6. Data and performance

CHANGE. The draft's "batch asynchronously so we do not starve 25 connections" describes a cost the write does not have.

The flow rows are CTEs of the message INSERT (`flow_postgres.go:11-13`): one statement, one connection, 0 extra round trips. A second async writer would add a connection. prd `max_connections` is 25 (`do_spl_db_query` at 17:11Z; the cnf states the same at `csi-spl-cnf/csi-spl/all.env.yaml:179,374-375`, tier `db-f1-micro`, hub pool 8). FORCE RLS is on both flow tables (`0104_flow_events.sql:49,58`).

Private bench, not the micro's CPU. `postgres:16-alpine`, server `PostgreSQL 16.15 on x86_64-pc-linux-musl`. Role `bench` (not a superuser), tables owned by `bench`, FORCE RLS, `app.tenant_id = t1`. Background 8457 rows, 4677 of them on one member, matching the prd counts. Indexes `flow_events_member_at`, `flow_events_msg`, `flow_events_place`.

Page read, `EXPLAIN (ANALYZE, BUFFERS)`, n = 1: `Index Scan using flow_events_member_at`, 30 rows, execution **0.061 ms**, buffers shared hit = 3 (planning hit = 29, read = 1).

Insert mean, `clock_timestamp` around 200 inserts of one line's watchers, same role:

| watchers | why this n | mean ms per line |
|---|---|---|
| 1 | prd agent p50 | 0.097 |
| 12 | prd agent p95 | 0.233 |
| 14 | t1 memberships | 0.309 |
| 32 | prd agent max | 0.481 |
| 666 | 14 members + 652 agent ids from the 17:11Z statement | 14.732 |

One `EXPLAIN (ANALYZE, BUFFERS)` of the 32-watcher insert: bitmap index scan on `flow_watches_pkey`, execution 1.780 ms, 32 rows. The 0.481 ms is the warm mean (n = 200). These milliseconds are a floor relative to `db-f1-micro`. The plan shape is the part that transfers: one index scan, one statement.

**Do not fan release out as rows.** Everyone sees the same line, so it is one read. Written as rows, the 7 d `committed_at` volume would be 2080 x 14 = 29120 human rows, or 602 versions x 14 = 8428, and 602 x 666 = 400932 if the 652 agent ids were included. The bench's 666-watcher insert is 14.7 ms on this box, per line, on the hot path. `versioned_at` plus a per-day fold (section 2) is one line a day and 0 extra writes on the message path.

Replace section 6 with:

> - **Fan-out.** Per-member rows only for `mention`, `poke`, `dm`, `reply`, `blocked` and `ready`, inside `flowInsertCTE` (0 extra round trips). prd fan-out 1.0303 (n = 8457 / 8208). Agents do not get `dm` or `reply` rows (section 5), so that 7.6x is not taken.
> - **Release.** No rows. The page read merges `release_notes` with `versioned_at` on the UTC day, one line per day. Badge for humans stays `flowCountsSQL` (`flow_postgres.go:112`). The draft's "one index-only scan anti-joined with read_marks" is not that function. Agents read counts with the page. This bench did not re-time the badge.
> - **Delete FR-008.** "Batched to respect the 25-connection limit" adds a connection the current write does not take.
