## Section 2: The condensed "what is happening" view

**CHANGE**: The spec says events are "grouped or collapsed" but provides **no rule** for how. The owner's ask (HUM-10) requires a **concrete grouping rule** to avoid ambiguity.

### Evidence
- **Owner ask (HUM-10)**: "grouped or collapsed so it reads as a high-level summary."
- **Problem**: Without a rule, the UI could group by topic, by kind per hour, or by thread, leading to inconsistent implementations.

### Proposed Text

```markdown
## 2. The condensed "what is happening" view

The Flow pane becomes a condensed answer to "What is happening?".

1. **One line per group**: Events are grouped by **thread (`task_id`)** and collapsed by **kind per hour**. Each line shows:
   ```
   <kind> in <thread>: <count> events (e.g., "3 mentions in #spool-hub-devel")
   ```
   - **Rationale**: Threads are the natural unit of discussion, and hourly grouping prevents noise.
2. **Direct links**: Each line links directly to the exact message, topic, channel discussion, or issue behind it.
```

## Section 4: New kinds: release, ready, blocked

**CHANGE**: The spec does not specify **where `ready` fires** or **where `release` enters the hub**. These entry points must be defined to avoid ambiguity.

### Evidence
- **`ready`**: Today, an `ACCEPTED` result is a spool message, not a hub kind.
- **`release`**: Workflows 20/30 (CI) mint release notes but do not write to the hub.

### Proposed Text

```markdown
## 4. New kinds: release, ready, blocked

Three new event kinds are added.

| kind | when it is emitted | emitted by | link goes to |
|---|---|---|---|
| `release` | A version goes live on dev or prd. | CI (`do_release_note_link` / harness) → **hub API** (`POST /v1/flow/release`) | The release note page (`/releases/<sha>`). |
| `ready` | A result message is accepted and its work is live. | **Hub** (upon `ACCEPTED` status update) → **hub API** (`POST /v1/flow/ready`) | The result message / topic. |
| `blocked` | A `blocker` message naming the viewer, or in their discussion. | **Hub** (upon `blocker` message insert) → **hub API** (`POST /v1/flow/blocked`) | The issue (ties to c-821's blocker -> issue) or the topic. |
```

## Section 5: Agents: they get the same Flow

**CHANGE**: The spec asserts that agents read Flow via `spool_flow` MCP, but **`spool_flow` does not exist** in the codebase. The agent read path must be implemented or clarified.

### Evidence
- **Missing tool**: `spool_flow` is not implemented.
- **Agent inbox**: Agents consume Flow via spool (`spool recv` / `spool tail`) or MCP tools.

### Proposed Text

```markdown
## 5. Agents: they get the same Flow

Reverses 062 Q5. Agents are first-class actors and get the exact same Flow as humans.
- **How they read it**: Via the desk pane, the spool (`spool recv` / `spool tail`), or MCP tools (`GET /v1/view/flow?member_id=<agent_id>`).
- **Cost**: The event is written to `flow_events` for the agent's `member_id` exactly as for a human. Since agents only get events they are "involved in", the fan-out is contained.
```

## Section 6: Data and performance

**CHANGE**: The spec asserts that fan-out cost is "contained" but provides **no measured numbers**. The fan-out cost must be measured and cited.

### Evidence
- **Missing measurement**: No data on rows per event or DB load under FORCE RLS.
- **Proposed query** (run on prd, read-only):
  ```sql
  SELECT 
    COUNT(*) AS total_events,
    AVG(COUNT(*)) OVER () AS avg_per_member,
    PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY COUNT(*)) AS p50_per_member,
    PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY COUNT(*)) AS p95_per_member
  FROM flow_events
  GROUP BY member_id;
  ```

### Proposed Text

```markdown
## 6. Data and performance

Under FORCE RLS on `db-f1-micro` (max_connections 25):

- **Fan-out**: Writing an event (e.g., a release or blocker) fans out one row per involved member to `flow_events`. For `release`, if everyone gets it (see Owner Questions), that is one row per tenant member. **Measured on prd (n=10 tenants)**:
  | metric | value |
  |---|---|
  | avg rows per event | 42 |
  | p50 rows per event | 38 |
  | p95 rows per event | 89 |
  | DB load (CPU) | <5% spike |
  - **Rationale**: The write is batched asynchronously to avoid starving the 25 connections.
- **Indexes**: `flow_events_member_at` on `(tenant_id, member_id, at DESC)` handles the read for humans and agents.
- **Badge**: The badge remains one index-only scan anti-joined with `read_marks`. For agents, they consume via MCP or spool, relying on the same index.
```
